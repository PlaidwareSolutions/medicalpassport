# Generating `@medpass/api-client` types from the OpenAPI document

Status: planned follow-up to Phase 0 ticket 0.13 (ADR-V2-013). Nothing in this
package is generated yet — the hand-written client in `src/index.ts` stays the
runtime surface until the steps below land in their own ticket, because this
package is under active edit and a generated `types.ts` would collide with
that work.

## What already exists

- `apps/api/openapi.json` — the pinned OpenAPI 3.1 document, regenerated by
  `pnpm --filter @medpass/api openapi:generate` and diffed in CI by
  `openapi:check`. Also served at `GET /v1/meta/openapi.json`.
- Every request body and Zod-validated query string is a named component
  (`#/components/schemas/OtpRequest`, `…/CreateMedication`, …) converted from
  the very Zod schema the controller parses with, so the request side is
  authoritative today.
- Response bodies are marked `x-response-schema-source: "hand-written"` (see
  `apps/api/src/openapi/schemas.ts`). They are deliberately loose
  (`additionalProperties` open, only the fields a client may rely on) and are
  provisional until a Zod response schema exists in `packages/validation`.
- Each operation carries `x-auth`, `x-step-up`, `x-rate-limit`,
  `x-profile-scope` / `x-admin-duty` extensions describing the guardrails, and
  the shared parameters (`x-profile-id`, `idempotency-key`, `x-client`,
  `x-requested-with`, `x-correlation-id`) are `$ref`s to
  `#/components/parameters/*`.

## How types will be generated

1. **Tooling.** `openapi-typescript` (type-only output, no runtime, OpenAPI 3.1
   aware). Add it as a devDependency of this package — not of the API — so the
   API never depends on its own client.
2. **Script.** `packages/api-client/package.json`:

   ```json
   "generate:types": "openapi-typescript ../../apps/api/openapi.json -o src/generated/openapi.d.ts --alphabetize --root-types"
   ```

   The output is committed (like `openapi.json` itself) so consumers do not
   need the API checked out to build; `--alphabetize` keeps the diff stable.
3. **Typed helpers.** `src/generated/index.ts` (hand-written, tiny) re-exports
   the useful shapes:

   ```ts
   import type { paths, components } from "./openapi";
   export type Schemas = components["schemas"];
   export type RequestBody<P extends keyof paths, M extends keyof paths[P]> = …;
   export type ResponseBody<P extends keyof paths, M extends keyof paths[P], S extends number = 200> = …;
   ```

   The existing `ApiClient` methods then annotate their bodies with these
   types one method at a time; nothing changes at runtime.
4. **CI gate.** Extend the API's `openapi:check` step (or add a sibling
   `types:check`) to run `generate:types` into a temp path and diff against
   the committed `src/generated/openapi.d.ts`, so a contract change cannot
   land without its regenerated types.
5. **Zod-first responses.** As response Zod schemas are added to
   `packages/validation` (they are the actual gap — see the
   `x-response-schema-source` counts in the document), the registry rows in
   `apps/api/src/openapi/registry.ts` switch `response:` from a hand-written
   fragment to the Zod schema, the generated types tighten automatically, and
   the runtime client can validate responses with the same schema.

## Non-goals

- Do not generate a runtime client (fetch wrappers, retries, cookie/CSRF
  handling live in `src/index.ts` and encode behaviour the spec does not —
  step-up retry, `x-requested-with`, cookie vs. bearer). Types only.
- Do not add `class-validator` / `class-transformer` DTOs to the API to feed
  `@nestjs/swagger`: Zod in `packages/validation` remains the single source of
  request validation (ADR-V2-013 chose Zod → JSON Schema for exactly this).
