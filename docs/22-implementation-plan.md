**Stage 5 (partial, this session):** `packages/offline-sync` — an IndexedDB wrapper (via `idb`) with four object stores: `medications` and `timeline` caches (both keyed by profile + a variant/date so "current" vs "all" medications and different days' timelines don't collide), a `mutations` outbound queue keyed by `clientMutationId`, and `meta` for last-synced timestamps. 11 unit tests against `fake-indexeddb`, run in a real (simulated) IndexedDB, not mocked-out function calls. `lib/timeline.ts` and `lib/medications.ts` now cache every successful fetch and fall back to the cache on a genuine network failure (distinguished from a server-side rejection: an `ApiError` means the server responded and is shown as a real error; anything else means `fetch()` itself failed, which is the offline signal). Recording a dose while offline queues the mutation instead of losing it — the same `clientMutationId` the API already required for idempotency (built in Stage 4) makes replay exactly-once safe even after the app is closed and reopened. `useSyncEngine` flushes the queue on app open, on the browser's `online` event, and on tab visibility change (docs/32's mandated fallback for browsers without Background Sync) and drives a genuinely honest status banner — online/offline/syncing/failed/pending-count/last-synced are real, distinct states, not a collapsed boolean.

Verified with an actual Chromium browser via Playwright (`context.setOffline(true)`), not just unit tests — offline behavior is fundamentally about browser network events and IndexedDB, which unit tests can't exercise end-to-end. This caught two real bugs before they shipped:
1. `SessionProvider` treated a network failure on a fresh page mount as "signed out" and redirected to `/welcome` — meaning reopening the app while offline looked exactly like being logged out, defeating the entire feature. Fixed: a network failure (not a 401) with a locally-stored profile id now stays "ready" and lets each screen serve its own cached data, since a stored profile id is evidence of a real prior session.
2. The pending-mutation count had no way to update when a new mutation was queued — `recordDoseEvent` and `useSyncEngine` are two independent hook instances with no shared state, so queuing a dose offline never refreshed the banner. Fixed with a small pub/sub event (`notifyMutationQueued`) that the sync engine listens for.

**Stage 6 follow-up, this session — schedule-conflict and dose-differs-from-prescription checks:** docs/09 names these as finding categories 9–10 but, unlike the interaction/allergy checks, never pins down their mechanics anywhere in the planning docs — so both are defined here purely from data the app already has, never fabricated, and documented as an explicit engineering judgment call alongside the rest of Stage 6's "requires clinical validation" caveat. **Schedule conflict**: fires when a fixed-frequency medicine (OD/BD/TDS/HS/PATTERN) has no active `MedicationSchedule` — the reminder infrastructure silently not matching what the confirmed instruction implies it should (`moderate`) — or when a PRN medicine has one anyway, contradicting "as needed" (`low`). **Dose differs from confirmed prescription**: compares a medicine's very first confirmed instruction against the one in force now (instructions are copy-on-write per docs/13, so this is a plain diff over the patient's own history) and flags if the dose or frequency changed, `moderate` severity — never a judgment about whether a doctor authorized the change, just that a change happened.

Found and fixed a real, pre-existing bug while wiring the finding titles for these two new categories: `FindingCard`'s title lookup is `t(\`safety.finding.${finding.category}\`)`, but the dictionary keys for the four original categories used shortened names (e.g. `safety.finding.exact_duplicate`) that never matched the real stored category strings (`exact_ingredient_duplication`) — so those titles have silently rendered as the raw, untranslated key string since Stage 6 shipped, for every category except `uncertain_normalization` (whose short name happened to already match). Never caught because this dev database had only ever produced `uncertain_normalization` findings until this session's live testing generated the others for real. A real, non-obvious config hazard surfaced while live-testing, not something a code review would catch: `OTP_DEV_FIXED_CODE` (development convenience — always returns "000000" so no real SMS is needed to sign in) is gated off only in literal `NODE_ENV=production` — pairing it with `OTP_TRANSPORT=sms` in any other environment (e.g. a staging environment doing real user testing) would text a real, unchanging, guessable code to whoever asks for one, at real per-message Telnyx cost, forever. Fixed by refusing that combination in `env.ts` regardless of `NODE_ENV`, the same fail-fast pattern the existing production-only guards already use.

Verified live against the real Telnyx API, twice, deliberately using the account's current unverified-number state as the test: (1) OTP — requested a real login code to a real US number through the actual `/auth/otp/request` endpoint with `OTP_TRANSPORT=sms` and no fixed code; Telnyx accepted and queued it (confirmed via the message ID and a `~700ms` real network round-trip, not an instant no-op), and a direct, separately-sent probe with the exact same call shape confirmed Telnyx's own status endpoint eventually reports `delivery_failed` with the true reason (`"Tollfree number is not verified"`, error 40329) — proving the send path is really live, not mocked, and that the code correctly surfaces that specific failure rather than a generic one. (2) Reminders — granted `sms_reminders` consent for a profile whose phone was the real test number, created a low-supply medicine, ran the real compiled `generate-refill-reminders` and `detect-due-reminders` binaries with real Telnyx credentials: the refill notification dispatched over SMS, Telnyx accepted it, and the `NotificationAttempt` recorded `status: sent` with the correct privacy-safe generic text — confirmed by independently sending a probe message with the identical text and polling its real (again toll-free-unverified) delivery outcome. 7 unit tests for `TelnyxSmsSender` (template selection, privacy-safe wording, locale variants, real Telnyx error-code propagation) and 6 e2e cases for the consent-to-channel cascade — full suite re-verified green (105 tests, 12 suites).

Not built at this point: WhatsApp (no WABA connected to check against), a delivery-status webhook receiver (the dispatch code only sees Telnyx's synchronous queue-acceptance result, not the async final delivery outcome that arrives by webhook minutes later — see the webhook receiver follow-up entry below, which closes this), and message-template localization beyond the two languages OTP already had (SMS reminder text is English-only, matching the same pre-existing simplification the push payload text has).

**Stage 4 follow-up, this session — Telnyx delivery-status webhook receiver:** closes the one gap above that's genuinely code-completable (WhatsApp isn't; real delivery in this account isn't). `NotificationAttempt` gains `providerMessageId` (Telnyx's message id, captured on every successful SMS send) so a later webhook call can find its way back to the exact attempt row it's reporting on. `TelnyxSmsSender` now accepts an optional `webhookUrl`, included as `webhook_url` on the send request when configured (`TELNYX_WEBHOOK_URL`, new in both the api and cron env shapes) — Telnyx calls back to that URL as the message's status changes.

`POST /v1/webhooks/telnyx/sms` (new `TelnyxWebhookController`) is necessarily unauthenticated — Telnyx has no session — so the only thing standing between it and a spoofed delivery report is verifying its Ed25519 signature (`telnyx-signature-ed25519`/`telnyx-timestamp` headers, signed over `"{timestamp}|{raw body}"`) against `TELNYX_PUBLIC_KEY` (from the Telnyx portal — confirmed also fetchable live via `GET /v2/public_key`, distinct from the API key). Verification runs against the *raw* request bytes, before any JSON parsing is trusted, which needed `rawBody: true` added to the Nest app bootstrap (`main.ts`) — this only adds `request.rawBody` alongside the normal parsed body, nothing else changes. Telnyx hands out the public key as a raw 32-byte value, not a PEM/DER blob; `verifyTelnyxWebhookSignature` (`@medpass/notifications`) prepends the fixed 12-byte ASN.1 SPKI prefix Node's `crypto.createPublicKey` needs to import a raw Ed25519 key, rather than reaching for a third-party library for one well-known constant. A missing/invalid signature is a `401`, not a silently-ignored `200` — this is the one place a wrong answer here is a real security gap, not a UX nicety. `parseTelnyxDeliveryOutcome` reduces the wider webhook payload to the one thing that matters: only `message.finalized` events with a `delivered` or `*_failed` status produce an outcome; `message.sent`/`queued`/`delivery_unconfirmed`, and any attempt id the webhook can't match (e.g. an OTP send, which never creates a `NotificationAttempt`), are accepted (`200`) and ignored rather than erroring.

Verified live: fetched the real Telnyx public key via `GET /v2/public_key` (matches the account's actual signing key, not assumed), sent a real SMS through the actual `TelnyxSmsSender` code path with `webhookUrl` set — Telnyx accepted the request and echoed `webhook_url` back in its response, confirming the field is wired correctly end-to-end on the send side — and confirmed the real public key imports cleanly through the new DER-wrapping code with no exception (a wrong prefix/length assumption would fail on import regardless of whose key it is), correctly rejecting a bogus signature. A genuine inbound webhook call from Telnyx's own servers wasn't exercised — that needs a real public HTTPS endpoint, which this sandbox doesn't have (same domain-placeholder gap as OD-1) — so the receiving side was verified with a self-generated Ed25519 keypair standing in for Telnyx's real one: same algorithm, same header/signing-string format (confirmed against Telnyx's current published docs, not assumed from training), same code path, proving the verify/parse/correlate logic is genuinely correct rather than merely plausible. 9 new unit tests (`packages/notifications`) and 7 new e2e cases (`telnyx-webhook.e2e-spec.ts`: missing signature, tampered signature, valid delivered/failed correlation, unmatched message id, non-finalized event) — full suite re-verified green (116 tests, 14 suites).

Not built: acting on a `failed` outcome (e.g. auto-revoking the channel the way a web-push subscription is revoked on a 404/410) — Telnyx's failure-code taxonomy isn't well-understood enough yet to safely distinguish "this specific number is permanently bad" from "temporary account-level block" (the toll-free-verification error being the obvious example), and revoking a channel on the wrong signal would silently stop reminding someone who could otherwise still be reached; a real webhook call arriving from Telnyx's own infrastructure (needs a real public domain — OD-1); and a live end-to-end delivery confirmation for this account, which is unreachable until the existing toll-free-verification/DLT platform gaps (see above) are resolved regardless of anything built here.

**Stage 4 follow-up, this session — missed-dose caregiver escalation + critical-severity quiet-hours bypass:** the two gaps this session's own quiet-hours work had flagged as unbuilt (see above). `reconcile-missed-doses` (previously a single `updateMany` with no visibility into which rows it touched) now fetches the newly-overdue rows first, flips them to `missed`, and — for each one — checks whether the patient has at least one caregiver holding `manage_reminders`/`full_management` scope; if so, creates a `pending` `caregiver_escalation` Notification (deduped on `${doseId}:escalation`, so a restart can't double-create one). No caregiver with that scope means nothing is created — there's no one to escalate to and no in-app surface of its own for this kind, matching how an empty recipient set is already handled everywhere else in the reminder system.

Dispatch reuses `detect-due-reminders`'s existing shared Pass 2 rather than a parallel send path: `caregiver_escalation` is added to the kinds it dispatches, with two differences from every other kind. Recipients are caregivers only, resolved by a new `resolveEscalationRecipients` (the profile owner is never a recipient of their own escalation — that would make no sense — and unlike `dose_reminder`/`refill`/`completion`, this doesn't gate on the patient's own `pushEnabled` preference, since that toggle is about reminders addressed to the patient, not a say over whether their caregiver hears about a missed dose). And quiet hours are bypassed entirely, but only when the specific medicine involved has `PatientMedication.criticalEscalation` set — a new boolean, **patient opt-in only, never an inferred clinical judgement of severity** (docs/16 calls this an "opt-in policy" for exactly this reason): a checkbox on Add/Edit medicine ("If I miss a dose of this medicine → Alert my caregiver immediately"), off by default, that the patient sets per medicine themselves. A `caregiver_escalation` notification with no recipients or a failed send is cancelled outright, same as `dose_reminder` (no standing in-app list backs it, unlike refill/completion's). `TelnyxSmsSender` gained a `caregiver_escalation` SMS template following the same generic/`full_name` privacy split as the other three.

Found and fixed one real pre-existing bug while wiring this up, not introduced by it: `TimelineService.recordDoseEvent`'s "any surface resolves the reminder" step used `notification.findFirst({ where: { scheduledDoseId } })`, resolving only one arbitrary notification per dose. Once a dose can carry both a `dose_reminder` and a `caregiver_escalation` at once, that silently left the second one stuck looking "sent" forever after the patient actually took the dose. Changed to `findMany` + loop so every notification tied to a dose event resolves together; a new e2e case seeds both kinds with `sent` attempts on the same dose and asserts both flip to `acknowledged`/`done` after one dose-record call — it would have caught this on its own if written first.

Verified live end-to-end against real Postgres data, the real compiled `reconcile-missed-doses`/`detect-due-reminders` binaries, and the real Telnyx API (not mocked): created two medicines for one patient, one `criticalEscalation: true` and one `false`, invited and accepted a real second account as caregiver with `manage_reminders`, gave the caregiver their own active SMS channel (granting `sms_reminders` consent on their own profile — channels are per-user, not per-relationship, so this works regardless of which profile the consent was granted through), set the patient's quiet hours to cover the entire day, and backdated both medicines' next dose past the 2-hour grace window. `reconcile-missed-doses` marked both doses `missed` and created exactly one `caregiver_escalation` Notification per dose. `detect-due-reminders` then dispatched the critical one immediately (`sent: 1`) — a real Telnyx API call, accepted (same toll-free-verification-pending queue-acceptance as the earlier Telnyx work, not a final delivery guarantee) — while leaving the non-critical one `pending`/deferred (`deferred: 1`), proving the bypass is keyed specifically to the flag and not applied blanket. Also gave the patient their own active SMS channel and repeated the critical case: the resulting attempt's `NotificationChannel` still traced back to the caregiver's `userId`, confirming escalation recipients really are caregiver-only even when the owner also has a channel available. 4 new e2e cases (`missed-dose-escalation.e2e-spec.ts`) plus 1 new unit test for the Telnyx template — full suite re-verified green (109 tests, 13 suites).

Not built: a way for the *caregiver* to acknowledge or dismiss an escalation from their own side (today it only resolves when the *patient's* dose gets recorded, same as any other notification), and escalating on anything short of the existing 2-hour missed-dose grace window (e.g. an earlier "at risk of missing" warning) — not asked for, and would need its own timing decision docs/16 doesn't specify.

**Stage 11 follow-up, this session — application-level rate limiting:** docs/14, docs/18, and docs/26 are all explicit that rate limiting is layered — "Cloudflare rate limiting (per-IP budgets per flow) → application rate limiting (per-account, per-device)" — and that **the application layer must stand alone**: "Cloudflare is never the only protection against account takeover or OTP abuse." Cloudflare isn't provisioned in this sandbox (OD/platform-config, same as Railway/R2), which made the app-level gap real rather than theoretical: `ERROR_CODES.RATE_LIMITED` existed in `packages/domain` since early in the project but was never once thrown, and `CatalogController`'s own file header already claimed "rate-limit protected at the edge + app" — an intention that had never actually been built.

A new `RateLimitBucket` table (fixed-window counter, `key` + `windowStart` unique) backs `RateLimitService.checkAndIncrement()` — originally specced against Redis (`rate:` key namespace, docs/25) but there's no Redis in this sandbox, so Postgres is the counter store instead, the same documented substitution already used for the background-job queue. The `upsert`'s `ON CONFLICT DO UPDATE ... count = count + 1` increments atomically at the database level, so concurrent requests in the same window can never under-count each other. A new `RateLimitGuard`, registered globally alongside `AuthGuard` (and running first, so abusive traffic is rejected before any auth-related DB work), only acts on routes carrying a new `@RateLimit({ name, limit, windowSeconds })` decorator — everything else passes through unaffected. It runs regardless of authentication status, since the flows that most need it — OTP request/verify, public share access — are intentionally `@Public()` and have no session to gate them at all.

Applied to every "protected flow" from docs/26's list that actually exists in this codebase today: OTP request (10/hour/IP — a new layer on top of the existing 5/hour/phone limit `AuthService` already had, which this doesn't replace) and verify (20/hour/IP, on top of the existing 5-attempts-then-lockout per OTP record), public share access (30/minute/IP, shared across the JSON and PDF variants of the same token — they're the same abuse vector), catalog search (60/minute/IP), prescription-upload authorization (20/hour/IP), and the Telnyx delivery-status webhook (120/minute/IP — defense-in-depth on top of the Ed25519 signature check, which is the real protection there; a flood of even correctly-rejected signature attempts still costs real CPU). Account recovery, admin login, export generation, AI explanation/translation, and data deletion/export are all named in docs/26 too but don't exist as endpoints in this codebase yet — nothing to rate-limit there until they're built. A new `cleanup-rate-limit-buckets` cron (daily) deletes rows older than 24 hours — generous headroom given every window in use is an hour or less.

A real cross-test-suite correctness issue surfaced while wiring this in, not a production bug: the existing e2e suite makes 13 `/auth/otp/request` calls across 11 spec files, all using **different phone numbers** (each file's own test phone) but running from the **same test-client IP** — meaning a per-IP OTP-request budget would have started silently failing unrelated, previously-green tests the moment total cumulative calls crossed 10 in one `--runInBand` process, regardless of which file "owned" the failure. Fixed by adding `rate_limit_buckets` to every e2e spec file's existing per-file `TRUNCATE` statement (they already reset `otp_attempts`/`sessions`/`users` etc. per file for exactly this isolation reason — this is the same pattern, not a new one).

Verified live against the real running API, not just the test suite: 62 real requests to the real catalog-search endpoint returned a real `429` with `retry-after: 49` on request 61 (limit 60/min); the resulting `rate_limit_buckets` row's `count` matched the real request count exactly; backdating that row's `window_start` 25 hours and running the real compiled `cleanup-rate-limit-buckets` binary deleted exactly that one row and left the others (still within the 24h retention) untouched. 6 new e2e cases (`rate-limit.e2e-spec.ts` — window enforcement, independent keys, window reset, atomic concurrent increments, a real `@Public()` route hitting its real limit end-to-end with the header present, and one budget's exhaustion not affecting another's) — full suite re-verified green (131 tests, 15 suites).

Not built: WAF, Turnstile, and Cloudflare's own rate limiting (all **Requires platform configuration** — Cloudflare isn't provisioned), rate limits on account recovery/admin login/export/AI explanation/translation (don't exist as endpoints yet), and a behavioral-detection layer beyond fixed budgets (docs/26 mentions this as the last layer; a fixed-window counter is the budget enforcement, not anomaly detection).

**Stage 11 follow-up, this session — accessibility audit + fixes:** docs/33 sets a WCAG 2.1 AA baseline against an explicit target user (an older adult with limited smartphone experience, plus low-literacy/low-vision/motor-difficulty/screen-reader users) and claims a contrast-validated palette and an accessible-by-construction component library. Both claims turned out to be *mostly* true — worth checking rather than trusting, since the existing component library (`packages/ui-web`) already does real, substantive accessibility work: mandatory labels on `TextInput`, ARIA live regions on `Banner`, a genuine `radiogroup`/`radio` pattern on `ChoiceGrid`, icons always paired with text on `BottomNav`, a real `:focus-visible` ring (not suppressed anywhere), and `prefers-reduced-motion` honored globally. The audit's job was finding what was still really wrong, not assuming the whole surface needed rebuilding.

Four concrete, *computed* (not guessed) findings, each fixed:

1. **`--color-border` (`#d4dbd8`) measured 1.41:1 against white** — real WCAG contrast-ratio math, not an eyeball check — against docs/33's own stated ≥3:1 non-text-contrast requirement for UI components. This is the sole visual boundary for every `TextInput`, `Card`, unselected `ChoiceGrid` option, and the `BottomNav` top border across all 41 screens — a real, wide-reaching gap despite the "contrast-validated palette" claim, which had evidently been checked for *text* pairs (all of which do genuinely pass, verified the same way) but not for this UI-component border. Darkened to `#8a8e8c` (3.32:1), same hue family, no redesign.
2. **The QR code `<canvas>` on the share-creation screen had no accessible name at all** — a screen-reader user would hit a silent, unlabeled graphic. Added `role="img"` + a real `aria-label` describing its purpose (the "copy link" alternative already existed right next to it, so this was a labeling gap, not a missing-alternative one).
3. **Two disclosure toggles (`DoseCard`'s "more options", the shares list's access-log expander) had no `aria-expanded`** — a screen reader has no way to say whether the content they reveal is currently shown. Added `aria-expanded` + `aria-controls` to both, wired to a real `id` on the controlled region.
4. **`ChoiceGrid` — every dose/frequency/food picker in the app — used one Tab stop per option** rather than the WAI-ARIA `radiogroup` pattern's roving tabindex (one Tab stop for the whole group; arrow keys move focus *and* selection within it). A screen reader announcing "radio button" sets that exact expectation; Tab-per-option isn't wrong in the sense of being unusable, but it's the wrong interaction model for what's announced. Rebuilt with a roving `tabIndex` (0 on the selected option, or the first before anything's chosen; −1 elsewhere) and `ArrowLeft/Right/Up/Down` + `Home`/`End` keyboard handling — one component, so the fix reaches every dose/frequency/food picker in the app at once.

Not attempted, and deliberately documented rather than silently skipped: `<html lang="en">` is static in the server-rendered `layout.tsx`, corrected to the real active locale client-side within milliseconds by `lib/i18n.tsx`'s existing effect (`document.documentElement.lang`/`dir`) — a real but narrow gap (a screen reader reading during the brief pre-hydration window, or with JS disabled, gets the wrong pronunciation/direction) that would need locale stored in a cookie and read by a Server Component to fix properly server-side; out of scope for an audit-and-fix pass given no cookie-based locale mechanism exists anywhere in the app today.

Verified live with a real Chromium browser, not just a code read: opened the real Add Medicine screen, confirmed exactly one `[role="radio"]` per visible `radiogroup` carries `tabindex="0"` (the rest `-1`) across all three grids on the page simultaneously; focused the frequency group's first option and pressed `ArrowRight` — real DOM focus moved to option 2 *and* `aria-checked` flipped, confirmed via `document.activeElement`; `ArrowLeft` moved correctly back. Opened the real share-creation flow and read the live-rendered canvas's `role`/`aria-label` directly from the DOM — both present exactly as authored. Read `getComputedStyle(document.documentElement).getPropertyValue("--color-border")` from the real running page and confirmed the new token value is what's actually served, not just what's in source. No dedicated unit tests were added (there's no existing test harness for `packages/ui-web`/`packages/design-tokens`, and this live, real-DOM verification is the stronger proof for interaction/rendering behavior a jsdom-based test would only approximate).

Not built: automated axe-core checks per screen (docs/33's own engineering-enforcement table calls for this in a Playwright suite; Playwright itself isn't a persisted project dependency yet — installed transiently for this session's live verification only, matching how it was used for the original Stage 5 build), `eslint-plugin-jsx-a11y` in CI, and the manual TalkBack/VoiceOver/200%-zoom/Urdu-RTL release-gate passes docs/33 specifies — all real release-gate items, not audit-and-fix work.
