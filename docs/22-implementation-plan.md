Found and fixed a real observability bug while verifying this stage's error-path tests: `LoggingInterceptor` read `res.statusCode` inside RxJS `finalize()`, which fires *before* `ProblemDetailsFilter` actually sets the status on a thrown-exception path — so every 4xx/5xx response has been logged as whatever Express's default (200) was since Stage 1, silently undermining every error-rate dashboard and alert this system would ever have. Fixed by moving the log line to the response's `finish` event, which only fires once the status is truly final regardless of the success/error path's internal timing; added 3 regression tests pinning this down directly (success path, thrown-exception path, and a synthetic "status changes between handler and finish" case matching exactly what was silently wrong before).

Not built in Stage 7: PDF export, WhatsApp-text export, security review (required before any of this is exposed to real doctors/pharmacists).

**Stage 5 (partial, this session):** `packages/offline-sync` — an IndexedDB wrapper (via `idb`) with four object stores: `medications` and `timeline` caches (both keyed by profile + a variant/date so "current" vs "all" medications and different days' timelines don't collide), a `mutations` outbound queue keyed by `clientMutationId`, and `meta` for last-synced timestamps. 11 unit tests against `fake-indexeddb`, run in a real (simulated) IndexedDB, not mocked-out function calls. `lib/timeline.ts` and `lib/medications.ts` now cache every successful fetch and fall back to the cache on a genuine network failure (distinguished from a server-side rejection: an `ApiError` means the server responded and is shown as a real error; anything else means `fetch()` itself failed, which is the offline signal). Recording a dose while offline queues the mutation instead of losing it — the same `clientMutationId` the API already required for idempotency (built in Stage 4) makes replay exactly-once safe even after the app is closed and reopened. `useSyncEngine` flushes the queue on app open, on the browser's `online` event, and on tab visibility change (docs/32's mandated fallback for browsers without Background Sync) and drives a genuinely honest status banner — online/offline/syncing/failed/pending-count/last-synced are real, distinct states, not a collapsed boolean.

Verified with an actual Chromium browser via Playwright (`context.setOffline(true)`), not just unit tests — offline behavior is fundamentally about browser network events and IndexedDB, which unit tests can't exercise end-to-end. This caught two real bugs before they shipped:
1. `SessionProvider` treated a network failure on a fresh page mount as "signed out" and redirected to `/welcome` — meaning reopening the app while offline looked exactly like being logged out, defeating the entire feature. Fixed: a network failure (not a 401) with a locally-stored profile id now stays "ready" and lets each screen serve its own cached data, since a stored profile id is evidence of a real prior session.
2. The pending-mutation count had no way to update when a new mutation was queued — `recordDoseEvent` and `useSyncEngine` are two independent hook instances with no shared state, so queuing a dose offline never refreshed the banner. Fixed with a small pub/sub event (`notifyMutationQueued`) that the sync engine listens for.

End-to-end verification: signed in, added a medicine, loaded the timeline online (caching it), went offline, reloaded the page (confirmed the offline banner and cache-served timeline — not a broken page), recorded a dose offline (confirmed the "saved on this device" indicator and the pending-changes banner), went back online (confirmed the banner cleared), and confirmed directly in Postgres that the dose event landed exactly once with the correct action.

Not built: a generic `/v1/sync` batch endpoint (only dose events are offline-capable — the highest-value single action; docs describe a fuller contract for future entities), offline medication add/edit, Background Sync API (retry-on-reopen is itself a documented fallback, not a shortcut), and storage-quota-based cache eviction.

**Stage 3 + 8, combined (this session):** `stored_objects`/`prescription_documents`/`prescription_extractions`/`extraction_candidates` tables + migration. `ObjectStorage` (Stage 1 interface) gains a second implementation, `LocalDiskObjectStorage`, alongside the existing R2 one — HMAC-signed tokens scoped to one object + one operation + a short expiry, mirroring real presigned S3/R2 URL semantics exactly, so production can swap in real R2 later with zero application-code changes outside the one factory function (ADR-12; no Docker available this session, so this stands in for MinIO). `DocumentsService`: authorize-upload → direct PUT → `complete` (never trusts the client's "done" claim — reads the bytes back, checks the real magic-byte signature against the declared content type, computes a sha256, quarantines on mismatch) → presigned download, all audited. `ExtractionService` runs real OCR (Tesseract.js, English only — no API key, no account, confirmed working before anything was built around it) synchronously in-request (a real deployment would push this to the worker queue; documented simplification), then applies deterministic, rule-based candidate detection — catalog brand/alias substring match, frequency pattern (`1-0-1`) or abbreviation (OD/BD/TDS/QID/SOS/HS) regex, food-instruction keyword match — never AI, never a guess presented as fact. Every candidate keeps the exact source line (`detectedText`) next to its proposal and requires an explicit per-field confirm/reject before it's used for anything (docs/09 §6); dose quantity/duration are deliberately never read from the photo (OCR digits are unreliable for a hazard-critical field) and stay a typed pick identical to manual entry. Creating a medication from an extraction requires the brand and frequency candidates specifically confirmed — an unrecognized medicine or an unconfirmed frequency falls back to the existing manual add flow rather than guessing. PWA: scan screen (kind picker, camera capture via `capture="environment"` or file/PDF choose, upload progress, processing status) and review screen (per-field detected-text quote + proposed value + Correct/Not this, dose picker, submit). Full audit trail per step (`document.upload_authorized/completed/downloaded`, `extraction.processed`, `extraction.field_confirmed/field_rejected`, `medication.created` with `source: "extraction"`) with no raw PHI in any context payload — verified directly against Postgres. 10 new e2e cases plus a real, non-mocked browser walkthrough (Playwright: sign in → photograph a synthetic prescription image → OCR → confirm all three fields → add the medicine → verify it and its correctly-derived dose schedule on `/medicines`).

Found and fixed a real correctness bug while testing the quarantine path: `completeUpload` threw the "invalid file" `ApiProblem` *inside* the `$transaction` callback that recorded the quarantine — Prisma rolls back the whole transaction when the callback throws, so the quarantine flag and its audit event were being silently discarded on every rejection, leaving the document stuck in `pending_upload` forever with no record of why. Fixed by committing the quarantine transaction first and throwing only after it succeeds; added a regression test asserting the quarantine status and audit row both persist across the failed request.

Not built: AI-based content simplification/translation and Indic-script/handwriting OCR (both **Blocked** on OD-11/OD-12 provider decisions). Async worker-queue OCR processing and PDF text extraction were synchronous-in-request/image-only limitations noted here originally — both are now built; see the async worker queue follow-up entry below.

**Stage 3 follow-up, this session — `cleanup-abandoned-uploads` cron:** reclaims storage from uploads that never finished — a presigned upload authorized but never completed/verified before its token expired, or a file quarantined for a bad signature and past a 7-day retention window. Idempotent (only touches rows still `pending`/`quarantined`) and matches docs/25's pre-planned hourly schedule and job name exactly. Required widening `LocalDiskConfig.baseUrl` to optional (a delete-only consumer like this job never presigns a URL) and extending `cronEnvShape`/`JobContext` so job functions can read validated config, not just `prisma`/`log`. **Stage 4 follow-up, this session — web push reminders:** `notification_channels`/`notifications`/`notification_attempts`/`notification_preferences` tables + migration, modeled on docs/13's full notification schema (all documented channel/kind/status enum values kept, even the ones not implemented) so adding SMS/WhatsApp later is additive, not a redesign. Web push needs no external provider or account — a self-signed VAPID keypair (`web-push`, generated once and never regenerated) is enough, unlike SMS/WhatsApp which are genuinely blocked on OD-10. `VapidWebPushSender` (`@medpass/notifications`, alongside the existing `OtpSender`/`LogOtpSender`) wraps the `web-push` library and turns a 404/410 response into an explicit `gone` signal rather than a generic failure. **Stage 5 follow-up, this session — incremental server→client sync, field-level conflict merging, storage-quota cleanup:** the three genuinely-buildable gaps the prior follow-up called out (Background Sync API and the SW update-notification UI remain not built — the former has no fallback-free value beyond what retry-on-reopen already covers, the latter is a separate, self-contained UI feature nobody asked for this pass).

This is a real, honest simplification, stated plainly rather than pretended away: there's no per-field version history to detect true disjointness against whatever the *other* edit touched, so the guarantee is narrower than a full CRDT-style merge — these specific fields are safe to re-apply unconditionally, not "provably non-conflicting with the other change." A conflict that can't be (fully) applied is removed from the mutation queue and parked in a new `conflicts` IndexedDB store instead of retried forever or silently dropped (docs/15 "needs your review") — a new `/sync/conflicts` screen lists each one with the medicine name, what couldn't be merged, and two actions: re-open the edit screen to reapply the change, or keep the current version.

*Storage-quota cleanup.* `navigator.storage.estimate()` is checked after every successful sync; past 80% of quota, the cache trims to just today's timeline and the "current medicines" list — the offline goal spec §19 actually names — dropping every other cached date and the "all medicines" history variant (never the mutation queue itself). **Stage 4 follow-up, this session — Telnyx delivery-status webhook receiver:** closes the one gap above that's genuinely code-completable (WhatsApp isn't; real delivery in this account isn't). `NotificationAttempt` gains `providerMessageId` (Telnyx's message id, captured on every successful SMS send) so a later webhook call can find its way back to the exact attempt row it's reporting on. `TelnyxSmsSender` now accepts an optional `webhookUrl`, included as `webhook_url` on the send request when configured (`TELNYX_WEBHOOK_URL`, new in both the api and cron env shapes) — Telnyx calls back to that URL as the message's status changes.

`POST /v1/webhooks/telnyx/sms` (new `TelnyxWebhookController`) is necessarily unauthenticated — Telnyx has no session — so the only thing standing between it and a spoofed delivery report is verifying its Ed25519 signature (`telnyx-signature-ed25519`/`telnyx-timestamp` headers, signed over `"{timestamp}|{raw body}"`) against `TELNYX_PUBLIC_KEY` (from the Telnyx portal — confirmed also fetchable live via `GET /v2/public_key`, distinct from the API key). Verification runs against the *raw* request bytes, before any JSON parsing is trusted, which needed `rawBody: true` added to the Nest app bootstrap (`main.ts`) — this only adds `request.rawBody` alongside the normal parsed body, nothing else changes. Telnyx hands out the public key as a raw 32-byte value, not a PEM/DER blob; `verifyTelnyxWebhookSignature` (`@medpass/notifications`) prepends the fixed 12-byte ASN.1 SPKI prefix Node's `crypto.createPublicKey` needs to import a raw Ed25519 key, rather than reaching for a third-party library for one well-known constant. A missing/invalid signature is a `401`, not a silently-ignored `200` — this is the one place a wrong answer here is a real security gap, not a UX nicety. `parseTelnyxDeliveryOutcome` reduces the wider webhook payload to the one thing that matters: only `message.finalized` events with a `delivered` or `*_failed` status produce an outcome; `message.sent`/`queued`/`delivery_unconfirmed`, and any attempt id the webhook can't match (e.g. an OTP send, which never creates a `NotificationAttempt`), are accepted (`200`) and ignored rather than erroring.

Verified live: fetched the real Telnyx public key via `GET /v2/public_key` (matches the account's actual signing key, not assumed), sent a real SMS through the actual `TelnyxSmsSender` code path with `webhookUrl` set — Telnyx accepted the request and echoed `webhook_url` back in its response, confirming the field is wired correctly end-to-end on the send side — and confirmed the real public key imports cleanly through the new DER-wrapping code with no exception (a wrong prefix/length assumption would fail on import regardless of whose key it is), correctly rejecting a bogus signature. **Stage 11 follow-up, this session — application-level rate limiting:** docs/14, docs/18, and docs/26 are all explicit that rate limiting is layered — "Cloudflare rate limiting (per-IP budgets per flow) → application rate limiting (per-account, per-device)" — and that **the application layer must stand alone**: "Cloudflare is never the only protection against account takeover or OTP abuse." Cloudflare isn't provisioned in this sandbox (OD/platform-config, same as Railway/R2), which made the app-level gap real rather than theoretical: `ERROR_CODES.RATE_LIMITED` existed in `packages/domain` since early in the project but was never once thrown, and `CatalogController`'s own file header already claimed "rate-limit protected at the edge + app" — an intention that had never actually been built.

A new `RateLimitBucket` table (fixed-window counter, `key` + `windowStart` unique) backs `RateLimitService.checkAndIncrement()` — originally specced against Redis (`rate:` key namespace, docs/25) but there's no Redis in this sandbox, so Postgres is the counter store instead, the same documented substitution already used for the background-job queue. The `upsert`'s `ON CONFLICT DO UPDATE ... count = count + 1` increments atomically at the database level, so concurrent requests in the same window can never under-count each other. A new `RateLimitGuard`, registered globally alongside `AuthGuard` (and running first, so abusive traffic is rejected before any auth-related DB work), only acts on routes carrying a new `@RateLimit({ name, limit, windowSeconds })` decorator — everything else passes through unaffected. It runs regardless of authentication status, since the flows that most need it — OTP request/verify, public share access — are intentionally `@Public()` and have no session to gate them at all.

Applied to every "protected flow" from docs/26's list that actually exists in this codebase today: OTP request (10/hour/IP — a new layer on top of the existing 5/hour/phone limit `AuthService` already had, which this doesn't replace) and verify (20/hour/IP, on top of the existing 5-attempts-then-lockout per OTP record), public share access (30/minute/IP, shared across the JSON and PDF variants of the same token — they're the same abuse vector), catalog search (60/minute/IP), prescription-upload authorization (20/hour/IP), and the Telnyx delivery-status webhook (120/minute/IP — defense-in-depth on top of the Ed25519 signature check, which is the real protection there; a flood of even correctly-rejected signature attempts still costs real CPU). Account recovery, admin login, export generation, AI explanation/translation, and data deletion/export are all named in docs/26 too but don't exist as endpoints in this codebase yet — nothing to rate-limit there until they're built. A new `cleanup-rate-limit-buckets` cron (daily) deletes rows older than 24 hours — generous headroom given every window in use is an hour or less.

A real cross-test-suite correctness issue surfaced while wiring this in, not a production bug: the existing e2e suite makes 13 `/auth/otp/request` calls across 11 spec files, all using **different phone numbers** (each file's own test phone) but running from the **same test-client IP** — meaning a per-IP OTP-request budget would have started silently failing unrelated, previously-green tests the moment total cumulative calls crossed 10 in one `--runInBand` process, regardless of which file "owned" the failure. Fixed by adding `rate_limit_buckets` to every e2e spec file's existing per-file `TRUNCATE` statement (they already reset `otp_attempts`/`sessions`/`users` etc. per file for exactly this isolation reason — this is the same pattern, not a new one).

Verified live against the real running API, not just the test suite: 62 real requests to the real catalog-search endpoint returned a real `429` with `retry-after: 49` on request 61 (limit 60/min); the resulting `rate_limit_buckets` row's `count` matched the real request count exactly; backdating that row's `window_start` 25 hours and running the real compiled `cleanup-rate-limit-buckets` binary deleted exactly that one row and left the others (still within the 24h retention) untouched. 6 new e2e cases (`rate-limit.e2e-spec.ts` — window enforcement, independent keys, window reset, atomic concurrent increments, a real `@Public()` route hitting its real limit end-to-end with the header present, and one budget's exhaustion not affecting another's) — full suite re-verified green (131 tests, 15 suites).

Not built: WAF, Turnstile, and Cloudflare's own rate limiting (all **Requires platform configuration** — Cloudflare isn't provisioned), rate limits on account recovery/admin login/export/AI explanation/translation (don't exist as endpoints yet), and a behavioral-detection layer beyond fixed budgets (docs/26 mentions this as the last layer; a fixed-window counter is the budget enforcement, not anomaly detection).

**Stage 5 follow-up, this session — service-worker update-notification banner:** the one remaining item from Stage 5's original scope that wasn't Background Sync API (which has no real fallback-free value here — retry-on-reopen, already built, is itself one of docs/32's mandated fallbacks, not a shortcut standing in for it). **Stage 4 follow-up, this session — auto-revoke an SMS channel on a confirmed permanent delivery failure:** the last named "not done" item from the earlier Telnyx delivery-status webhook follow-up. Web push already revokes a subscription on a 404/410; SMS had the webhook recording `delivered`/`failed` outcomes but never acting on `failed`, deliberately deferred because Telnyx's failure-code taxonomy wasn't understood well enough to safely tell "this destination number is dead" apart from "temporary account-level block" — the one real code seen in this account, 40329 (toll-free not verified), is itself an account-level block, not evidence of anything about the destination.

Rather than guess, fetched Telnyx's own published messaging error-code reference directly (support.telnyx.com/en/articles/6505121) before writing any classification logic. Built a deliberately narrow **allowlist** (`PERMANENT_DESTINATION_FAILURE_CODES` in `@medpass/notifications`) of only the codes confirmed destination-specific and permanent: `40001` (landline/non-routable), `40012` (destination number unowned/deactivated), `40300` (recipient sent STOP — also a consent/compliance requirement to honor), `40310` (malformed 'to' address) — an allowlist rather than "everything except a known-safe list" because a false positive here silently stops reminding someone still reachable, a worse failure mode than reacting slowly to a genuinely dead number. `40329` stays excluded, as does `40003` ("blocked as spam — permanent") despite the name — Telnyx's own text says that one permanently blocks the *sending* number, not the destination, so treating it as a per-recipient signal would have been exactly the kind of mistake this deferral was guarding against.

`recordTelnyxDeliveryOutcome` (`apps/api/src/modules/notifications/notifications.service.ts`) now runs inside a transaction: updates the `NotificationAttempt` as before, and — only for a `channel: "sms"` attempt with a confirmed permanent-destination failure — guarded-updates the linked `NotificationChannel` to `status: "revoked"` (`updateMany` with `status: { not: "revoked" }` in the `where`, so a retried/duplicate webhook delivery can't write a second audit event) and writes a new `notification.channel_revoked` audit event (`actorType: "system"`, since this is an automatic consequence of a delivery outcome, not a user action) — closing a real gap the web-push revoke path already had (it writes no audit event at all; this one does). No new "is this channel revoked" check needed anywhere else: `resolveRecipients`/`resolveEscalationRecipients` in `apps/cron`'s `detect-due-reminders.ts` already only ever select `status: "active"` channels, so a revoked SMS channel is automatically excluded from every future send.

Tested: 4 new unit tests in `packages/notifications` (40329 explicitly asserted `permanentDestinationFailure: false`, a STOP code asserted `true`, the sending-number-blocked 40003 asserted `false`) plus 3 new e2e cases in `telnyx-webhook.e2e-spec.ts` (a STOP-code webhook revokes the channel and writes exactly the expected audit event; a 40329 webhook leaves the channel `active`; the same STOP webhook delivered twice writes only one audit event, not two) — full suite green throughout (170 api tests, 19 notifications unit tests). Deployed to both `medpass-dev` and `medpass-prod` and confirmed live.

**Real production incident found and fixed during this deploy — audit hash-chain race condition (runbook R7):** pushing the above triggered both environments' auto-deploy (confirmed standing behavior), and `medpass-prod`'s nightly `cron-verify-audit-chain` job — which redeployed onto the new commit and ran — reported the hash chain broken at seq 97, logging "treat as P1 incident (runbook R7)". Root cause: `writeAudit()` (`packages/audit/src/index.ts`) read the current chain tail and then inserted a new row pointing to it, with nothing serializing that read-then-append across concurrent callers — several of the caregiver's simultaneous requests each independently read the same tail before any of them committed, so three new rows all chained to the same predecessor instead of to each other. `medpass-dev`'s chain stayed intact only because it hadn't yet seen a comparable concurrent-write burst, not because the code was safe there.

Fixed by wrapping the read+insert in a Postgres transaction-scoped advisory lock (`pg_advisory_xact_lock`, keyed by a fixed constant), serializing every writer project-wide: when `writeAudit` is handed an already-open caller transaction, it acquires the lock on that same transaction (held until the caller's whole business transaction commits, matching the existing "audit write failure fails the operation" design intent); when handed the plain client directly (most call sites — the audit write has no larger business transaction to join), it opens its own dedicated transaction for exactly the lock+read+insert. This makes the entire audit log a strictly serial append point, which is the correct tradeoff for a single hash-chained ledger — it cannot be parallelized without abandoning the chain invariant itself.

Tested: a new `audit-chain-concurrency.e2e-spec.ts` reproducing the exact production scenario — 20 concurrent `writeAudit` calls via the plain client (no ambient transaction, mirroring `profile-access.service.ts`'s real call site) and, separately, 20 concurrent calls each inside their own ambient transaction — both asserted to leave `verifyAuditChain` intact. Confirmed the test actually catches the bug, not a false positive: temporarily reverted the fix and reran — both cases failed (one produced fewer distinct row hashes than writes, i.e. two callers computed and wrote the identical row; the other left the chain genuinely broken) — then restored the fix and confirmed both pass again. **Audit-chain acknowledgment, this session — stopping the nightly cron-verify-audit-chain crash emails without weakening the check:** the user reported repeated "Deploy Crashed" emails for `cron-verify-audit-chain` on `medpass-prod`. Root cause: exactly the seq-97 break fixed above — the nightly job re-scans the whole chain, finds that same historical break every night, and correctly exits non-zero since a broken chain is a P1 condition. But a hash chain can't be repaired retroactively, so without a way to say "this break is investigated and accepted," the job would alert on the same known fact forever.

This went through two corrections before landing on the real shape, each one caught by actually verifying against the real production database rather than trusting the design in the abstract:

1. First pass added a single `acknowledgedBreakAtSeq` param and set it to `97`. Running the deployed job against real data (`railway run` with the internal `DATABASE_URL` overridden to the public proxy, since local access can't reach Railway's private network directly) immediately returned `brokenAtSeq: 98` — re-examining the rows showed seq 96-99 all share the identical stale `prevHash`; one incident had misdirected three consecutive rows, not one, since all four concurrent writers read the same pre-incident tail before any of them committed (only row 96 happens to be genuinely correct — it really was first to reference that tail).
2. Second pass widened this to an acknowledged *set* of seqs and set it to `97,98,99`. Running the deployed job again returned `brokenAtSeq: 109` — a second, separate concurrency incident nineteen minutes after the first (same day, same root cause, a different caregiver session). Rather than keep discovering breaks one redeploy at a time, wrote a one-off local script that repeatedly calls `verifyAuditChain`, acknowledging each break as it's found, until the whole chain is scanned — surfacing **210 total historical breaks**, every one dated between 2026-07-24 and 2026-07-25T16:26, and *none* after. The fix (the advisory-lock commit above) deployed the next day; every row since — 89 of them across more than a full day of real traffic — has stayed perfectly chained. That clean cutover, with zero exceptions on either side of it, is itself strong evidence this is exactly the mechanical concurrency signature already diagnosed, not something new or suspicious: ordinary concurrent page-load traffic hit the same pre-existing, deterministic race repeatedly across the pilot's early operation, at a rate that just happened to be high enough to produce this many instances before anyone had a tool that could see past the first one.

An enumerated set of 210 seqs doesn't scale operationally, so the real design is a **boundary**, not a list: `verifyAuditChain()` takes `acknowledgedBreaksBeforeSeq?: bigint` — any break at or before that seq resumes from the row's own `rowHash`; anything after it still fails loudly. Set to `683` (the actual last historical break) on `medpass-prod` only; `medpass-dev`'s chain has stayed intact throughout, so it's left unset there.

**Visual dose and timing on the medicine tile, this session (docs/07 screens 9/10, docs/33):** the user asked whether medicine tiles could show form icons (tablet/syrup/injection) and represent the quantity visually, "so it is very clear and obvious to less educated people as well." Research found this is not a new idea but an **unbuilt commitment**: docs/01's persona P3 (Fatima, 55, low literacy, Urdu-first) already lists "icons with labels" as a design implication, and docs/33 already promised "dose patterns localized (1-0-1 grid shown visually: sun/plate/moon icons + text)" — with `proposeSlots`/`parsePattern` sitting in `packages/medication-terminology` since Stage 2 with **no visual consumer at all**. So the time-of-day half was a spec item; only the form glyph was genuinely new (docs/07 screens 9/10 specify text-only tiles).

**A read-only query against the production pilot shaped the design more than anything else.** Of 32 active medicines: **not one** is linked to a catalog product with a known dosage form, so the glyph had to key off the stored `doseUnit` alone; **22 of the 30 "tablet" rows predate the 2026-07-24 type-picker fix** (`10afc28`), when the app hardcoded `doseUnit: "tablet"` on every save, making "tablet" a leftover default rather than anyone's choice; and **30 of 32 (94%) resolve to unambiguous time slots**, so the new row genuinely renders rather than mostly hiding. The legacy-default problem was put to the user, who chose to ship the icons anyway — the glyph depicts the same stored value the text line already showed, so it adds no new inaccuracy — with a confirm-your-medicine-type prompt left as follow-up.

**The bug the plan review caught, which is the substantive part of this change.** The first design gated the time-of-day row on `proposeSlots(...) !== null`. That is wrong: `WEEKLY`, `FORTNIGHTLY` and `MONTHLY` all return `[{morning, 1}]`, and that function's own comment explains why — it proposes only a *time of day*, while *which days* come from the medication's start date via the scheduler's `anchorDate`. A list tile has no anchor date, so a monthly injection would have drawn a lone sun asserting "every morning" — a false statement about a dose, which docs/10 H-06 rates catastrophic. Replaced with an explicit `hasFixedDailySlots` allowlist (OD/OD_AFTERNOON/BD/TDS/HS/PATTERN) and a regression test that asserts `proposeSlots` still returns non-null for the three while the allowlist refuses them. No production medicine used those frequencies yet, but the add screen offers all three.

**The second honesty rule:** `proposeSlots` returns a per-slot *multiplier*, not a dose, so the real amount is `doseQuantity × slot.quantity`. For every frequency reachable from the patient UI the slots are uniform, but an OCR-extracted or API-supplied `2-0-1` is not — and a single "1 tablet" headline beside it would misstate the morning dose. When slots aren't uniform the headline is suppressed entirely and the amount moves into each slot, which is precisely docs/33's "1-0-1 grid". Glyph repetition is likewise limited to tablet/capsule — the same countable/measured split the add screen already makes — because repeating a cup five times for "5 ml" would draw a quantity that doesn't exist.

**Hand-drawn SVG rather than the app's existing emoji convention**, deliberately: there is no inhaler emoji and no way to tell syrup from injection; emoji colour can't be controlled and docs/33 requires ≥3:1 for non-text (the brand green measures 6.46:1 on white, 6.06:1 on a card — computed, not assumed); and the target device is an old Android whose WebView emoji coverage varies. Sized in `em`, not px, so glyphs scale with text at 200% — verified growing 21px → 43px. The first draft of the syrup glyph was a spoon and **read as a magnifying glass at 16 px** (an ellipse on a stick is a lens on a handle); redrawn as a tapered medicine cup, with the syringe flattened and the inhaler simplified after the same screenshot review. A comment reserves fork-and-knife for docs/07 screen 8's future food-instruction icon so it can never collide with the plate that means midday here.

**Zero new localization keys** — `unit.*` and `timeline.slot.*` already existed in all four dictionaries, and building the accessible name out of visible text (rather than a hand-maintained `aria-label` on the Card, which would have silently dropped the ingredient line and needed recomposing on every future content change) meant none were needed. The tile now reads "Uneven Tablet, Current, Morning, 2 tablet, Night, 1 tablet, …" to a screen reader.

Tested: 19 new vitest cases in `packages/medication-terminology` covering every row of the render matrix (33 in the package total). Verified in a real browser against the compiled API with 14 seeded medicines covering the whole matrix — including `2-0-1` and `MONTHLY`, which the patient UI can't create and which had to be inserted through the API: 12 of 14 render a slot row and the two that don't are exactly the monthly and as-needed ones. Checked at 320 px in en/hi/te/ur with Urdu RTL mirroring correctly and no horizontal overflow, and at 200% text zoom. **A pre-existing 200%-zoom overflow was found and deliberately not fixed here:** at doubled root font size the current/previous tab buttons, the `Chip` component and the bottom-nav links exceed the viewport — on Home and Profile too, which this change doesn't touch (Profile is worst at 591 px against a 320 px viewport). None of the new elements overflow. That is an app-wide `ui-web` issue and wants its own change rather than being smuggled into this one. *(That change has since happened — see the reflow follow-up entry below.)*

**Confirm-your-medicine-type, this session (docs/07 screen 9):** the follow-up the visual-dose work made necessary. A read-only production query had found that 27 of 32 active pilot medicines carry `dose_unit = 'tablet'` written before the 2026-07-25 type-picker fix (`10afc28`), when every save hardcoded it — so for most pilot medicines "tablet" is a leftover default rather than anyone's choice. Harmless while the unit only rendered as text nobody could misread; not harmless once the tile draws it as a picture, which is trusted by precisely the low-literacy patient the glyph exists for.

**A live bug found while building it, and fixed here:** the scan-review screen (`app/add/scan/[documentId]/page.tsx`) *still* hardcoded `doseUnit: "tablet"` on submit — the same defect `10afc28` fixed for add/edit, but that path was missed and has been silently mislabelling every photographed prescription since. Without fixing it the prompt would have been mopping up a leak that was still running. It now offers the same medicine-type picker, and the quantity widget switches between the ½/1/2 tiles and a decimal input on the same countable/measured split the add screen uses — otherwise a patient picking "ml" would have been trapped choosing between 0.5, 1 and 2 ml.

**The mechanism is a fact in the data, not a date in a conditional.** New `MedicationInstruction.doseUnitConfirmedAt` records whether a human actually chose the unit, distinct from the existing `confirmedAt` which is stamped on every instruction regardless. The migration backfills it only where it can be *known*: any non-tablet unit (the hardcoded default was `tablet`, so ml/unit/puff can only have come from a person) or anything written on or after the fix. Everything else stays null and gets asked about rather than guessed — 27 rows in production, 5 auto-confirmed. Now that all three creation paths present a picker, the API stamps it on create and update; the schema comment records that invariant explicitly, because a future creation path that defaults the unit must leave it null.

**Confirming and correcting are deliberately different operations.** Confirming the unit already stored changes no clinical value, so it stamps the existing instruction — a superseding copy identical in every field would pad the medicine's history with a non-event. Correcting it to a different unit *is* a change to how the dose reads, so it supersedes copy-on-write and leaves the old row intact (docs/13). The endpoint takes only `doseUnit`: confirming a type must never become a back door to editing a dose, which has its own audited path.

The prompt itself is an info card at the top of the medicines list linking to `/medicines/confirm-type`, one medicine per screen (docs/33 "one primary action per screen"), each option showing its own glyph so the answer can be given without reading — the whole point. Offered once at the top rather than badged on every affected tile, since 27 of 32 would have carried a badge and buried the list.

**Follow-up the same session, after the user asked how the prompt would ever go away:** the honest answer was "only by answering every one" — no dismiss, no snooze, no expiry — and checking that surfaced a defect. The banner counted *every* non-deleted medicine, including stopped and completed ones. In production 2 of the 27 were `stopped`, both belonging to one patient, who would have been asked to classify medicines they no longer take and whose card could never reach zero without it. Now scoped to `current` and `paused` (paused resumes, so its type still matters). The predicate moved to `needsDoseUnitConfirmation` in `packages/medication-terminology` — taking `status` and the flag rather than the DTO, so it lives where there is a test runner — and the API deliberately still reports `doseUnitConfirmed: false` for a stopped medicine: it states the fact, the client decides whom to ask.

Tested: new `dose-unit-confirmation.e2e-spec.ts` (9 cases) covering the flag, the stamp-in-place path asserted by instruction *row count*, the supersede path asserted on both rows with the dose confirmed untouched, an invalid unit rejected, and a `view_medications`-only caregiver able to see the flag but 403 on answering. Verified live in a real browser: three legacy-looking medicines prompted one at a time, the count decrementing, two corrections and one confirmation applied, the tiles re-rendering with the corrected glyph, and the banner disappearing when none remain. 8 new localization keys × 4 languages.

**Stage 11 follow-up, this session — app-wide 200%-zoom reflow fix + the persisted Playwright accessibility suite:** the DoseVisual entry above measured and deliberately deferred a real WCAG failure — at doubled root font size the current/previous tab buttons, the `Chip` component and the bottom-nav links overflowed a 320 px viewport, Profile worst at **591 px against 320 px** — while docs/33 promises "all flows completable at 200% text zoom and 320 px width" and docs/07 makes "renders correctly at 320 px width" a shared acceptance criterion for all 41 screens. This change retires that deferral app-wide, and in doing so finally builds the axe-core-in-Playwright suite docs/33's engineering-enforcement table has promised (and this document has recorded as "not built") for three sessions running.

The overflow had three mechanical causes, none of them "the text is too big":

1. **`min-width: auto` floors everywhere.** `minWidth: 0` appeared *zero* times in the codebase, so every `flex: 1` tab, every bare-`1fr` grid column (`BottomNav`'s `repeat(5, 1fr)`, `ChoiceGrid`, Profile's `"1fr 1fr"` language grid) and every `justifyContent: "space-between"` card header was floored at its min-content width and could not shrink below it. Fixed with `minmax(0, 1fr)` on grids and `minWidth: 0` (usually with `flexWrap: "wrap"`) on the text side of card-header rows — `DoseCard`, `FindingCard`, `CaregiverAlertCard`, the medicines list tile, Profile's device rows, `PageHeader` (which also lost the app's only `whiteSpace: "nowrap"`).
2. **Unbreakable single words.** Once boxes could shrink, the residual overflow was words that exceed a 288 px line at doubled font all by themselves — "Hydrochloride" in a medicine name, "immediately" in a ChoiceGrid option, Telugu compounds like "గుర్తించలేకపోయాము". One inherited global rule, `overflow-wrap: break-word` on `body`, resolves all of them and is invisible until a word alone can't fit its line. Deliberately *not* done instead: converting the px spacing tokens to rem — under text-only zoom rem gutters double too and consume more of the 320 px, making reflow worse, and under page zoom px and rem scale identically anyway.
3. **Three horizontal rows with no wrap or scroll escape.** The medicines tablist, the bottom nav and Profile's device-chip row simply had nowhere to go but sideways. The tab rows are replaced by a new shared `Tabs` component in `packages/ui-web` — WAI-ARIA tabs pattern with the same roving-tabindex/arrow-key model `ChoiceGrid` already uses, wrapping `flex` layout — adopted at all three ad-hoc tab sites (medicines, blood-sugar, admin content). Adopting it on blood-sugar also fixed a real pre-existing a11y bug: its "tabs" were two plain Buttons with no `role="tab"`/`aria-selected` at all. `BottomNav` changed from `position: fixed` with a hard 64 px height to **sticky-in-flow and self-sizing**: `AppShell` became a flex column with the nav as its last child, the `repeat(auto-fit, minmax(min(100%, 3.3rem), 1fr))` grid keeps one row of five at normal text size and reflows to 3 + 2 at 200%, and `AppShell`'s manual `paddingBottom: calc(var(--bottom-nav-height) + …)` hack is deleted outright because the bar now occupies real layout space at whatever height it needs. `Chip` gained `maxWidth: "100%"` so a status pill wraps its label rather than widening its row.

**The measuring instrument is the deliverable as much as the fix.** Playwright (`@playwright/test` + `@axe-core/playwright`) is now a real, persisted dependency of `apps/patient-web` with a config, a global setup and two specs in `apps/patient-web/e2e/`. The suite runs against the real stack, not mocks: the global setup logs in through the actual OTP flow (`OTP_TRANSPORT=log`, fixed dev code, a fresh random phone per run to stay clear of per-phone resend limits), creates a profile and seeds one medicine through the real API with deliberately hostile strings ("Metformin Hydrochloride Extended Release 500mg", prescriber "Dr. Ramachandran Venkatasubramanian") — min-content width being the failure mode under test, the seed data is chosen to provoke it. The reflow spec then loads **29 routes × 4 locales = 116 tests**, each at a 320 px viewport with the root font set to 200% (a faithful reproduction of browser text scaling for this stylesheet, whose fonts are all rem and spacing all px), and asserts `document.scrollWidth ≤ 321` *plus* — because `position: fixed`/`sticky` elements never widen `scrollWidth` — that no fixed or sticky element's rect escapes the viewport, so an overflowing nav cannot hide from the document-level measurement. The axe spec runs axe-core on all 29 routes and fails on any serious/critical violation, exactly the threshold docs/33 names. Both run in CI after the existing test step, reusing the job's postgres and env; Playwright boots the built API and web app itself via its `webServer` config.

The first full run of the new suite failed 16 of 116 reflow tests — which is the point of building it. Beyond the three known offenders it found four more screens overflowing that no one had measured (`/caregivers/new`, `/profile/dependents/new`, `/share/new`, `/medicines/[id]/edit`), each diagnosed to a concrete element before fixing: the relationship `ChoiceGrid`'s five one-word columns, the share-expiry Button row missing `flexWrap`, the edit screen's frequency picker. After the fixes: **116/116 reflow, 29/29 axe, zero serious/critical.**

Verified live beyond the assertions: real 320 px × 200% screenshots of Home (en), Profile (en, ur) and Medicines (te) — the bottom nav genuinely reflows to two rows and stays pinned while scrolling, Urdu RTL mirrors correctly with the sticky nav in flow, and the seeded worst-case medicine name wraps inside its Card instead of pushing the page sideways.

**Instant-feel navigation, this session — a stale-while-revalidate data layer (docs/15-adjacent):** the user reported page switches feeling slow. Measured against production first: the navigation itself was cheap (~72 ms RTT through Cloudflare, 2.2 KB RSC payloads, immutable JS chunks served from edge cache), so the cost was the data layer — every hook was a `useEffect`-fetch-on-mount with no shared cache and no in-flight dedupe, so every navigation spun until the network answered even for data fetched seconds earlier; the IndexedDB offline cache was consulted **only on network failure**, never for instant render; Home fired ~9 requests a visit (several from AppShell, repeating on every page); and the medicines screen fetched its list twice (`?status=current` + unfiltered — a plain server-side equality filter, derivable client-side).

**The fix is one small hand-rolled utility, not a data library**: `lib/data-cache.ts` — a module-level `Map` keyed `` `${profileId|user}|${path}` `` with in-flight dedupe, adopted by all 18 mount-fetch hooks with their return shapes unchanged (no consumer edits). Cached data renders synchronously; with the default `ttlMs: 0` every mount still revalidates, so **freshness is not traded for the instant render** — only the two AppShell invitation hooks get a 60 s TTL (`scope: "user"`, phone-keyed, deliberately surviving profile switches). Medications/timeline additionally seed from their existing IndexedDB cache on cold start; the network-failure fallback path (docs/15 offline banner) is byte-for-byte unchanged, and fallback data is never written into the memory layer so it can't later masquerade as fresh.

**The safety constraints shaped the design more than the performance did.** docs/10 H-13 (wrong-patient data must never survive a profile switch, even one frame): keys are profile-scoped and `ProfileKeyedContent` already remounts the tree, so a switch can only ever read the new profile's keys — asserted in vitest by stubbing the active profile and proving A's entries are invisible under B. Sign-out/revocation purge the memory layer in `clearLocalState()`, the same choke point that clears IndexedDB. Every mutating helper invalidates its prefixes (a medication mutation drops the lists, detail rows, timeline and safety findings), and the REMOTE_CHANGE listeners invalidate before reloading so an unmounted consumer can't resurrect a known-stale copy (docs/12 H-12 — the cost is one honest spinner there).

**The medicines screen now issues one request** — its "current" tab is derived client-side — with one subtlety: that screen had been the second writer of the IndexedDB `"current"` variant that offline Home and the low-storage trim (`trimToEssentials`) depend on, so the `"all"` fetch now writes the derived `"current"` variant too, keeping offline Home intact without the second request.

Deliberately not built (flagged, not forgotten): the sync engine's empty-queue `POST /v1/sync` on every AppShell mount (changing it alters sync semantics — its own decision); the bundle diet (all four locale dictionaries ship to every user, 110 KB of polyfills, static `qrcode` import); server-side work. Vitest was added to patient-web (mirroring `packages/offline-sync`) since the pure cache core deserved real unit tests — 10 cases — and a new Playwright spec (`e2e/instant-nav.spec.ts`, 4 cases, run against the real compiled API + built Next app via the repo's own harness) proves the substance: a warm navigation renders the medicine list while every API response is deliberately delayed 4 s (render-before-network, asserted, not assumed); the medicines screen makes zero `?status=current` requests and tab switches cost nothing; three navigations inside the TTL produce no repeat invitation traffic; and a warm screen still renders with the network fully offline (docs/15 parity). Full Playwright suite 149/149 green alongside.
