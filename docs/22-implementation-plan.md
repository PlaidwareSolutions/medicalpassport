Found and fixed a real observability bug while verifying this stage's error-path tests: `LoggingInterceptor` read `res.statusCode` inside RxJS `finalize()`, which fires *before* `ProblemDetailsFilter` actually sets the status on a thrown-exception path — so every 4xx/5xx response has been logged as whatever Express's default (200) was since Stage 1, silently undermining every error-rate dashboard and alert this system would ever have. Fixed by moving the log line to the response's `finish` event, which only fires once the status is truly final regardless of the success/error path's internal timing; added 3 regression tests pinning this down directly (success path, thrown-exception path, and a synthetic "status changes between handler and finish" case matching exactly what was silently wrong before).

Not built in Stage 7: PDF export, WhatsApp-text export, security review (required before any of this is exposed to real doctors/pharmacists).

**Stage 5 (partial, this session):** `packages/offline-sync` — an IndexedDB wrapper (via `idb`) with four object stores: `medications` and `timeline` caches (both keyed by profile + a variant/date so "current" vs "all" medications and different days' timelines don't collide), a `mutations` outbound queue keyed by `clientMutationId`, and `meta` for last-synced timestamps. 11 unit tests against `fake-indexeddb`, run in a real (simulated) IndexedDB, not mocked-out function calls. `lib/timeline.ts` and `lib/medications.ts` now cache every successful fetch and fall back to the cache on a genuine network failure (distinguished from a server-side rejection: an `ApiError` means the server responded and is shown as a real error; anything else means `fetch()` itself failed, which is the offline signal). Recording a dose while offline queues the mutation instead of losing it — the same `clientMutationId` the API already required for idempotency (built in Stage 4) makes replay exactly-once safe even after the app is closed and reopened. `useSyncEngine` flushes the queue on app open, on the browser's `online` event, and on tab visibility change (docs/32's mandated fallback for browsers without Background Sync) and drives a genuinely honest status banner — online/offline/syncing/failed/pending-count/last-synced are real, distinct states, not a collapsed boolean.

Verified with an actual Chromium browser via Playwright (`context.setOffline(true)`), not just unit tests — offline behavior is fundamentally about browser network events and IndexedDB, which unit tests can't exercise end-to-end. This caught two real bugs before they shipped:
1. `SessionProvider` treated a network failure on a fresh page mount as "signed out" and redirected to `/welcome` — meaning reopening the app while offline looked exactly like being logged out, defeating the entire feature. Fixed: a network failure (not a 401) with a locally-stored profile id now stays "ready" and lets each screen serve its own cached data, since a stored profile id is evidence of a real prior session.
2. The pending-mutation count had no way to update when a new mutation was queued — `recordDoseEvent` and `useSyncEngine` are two independent hook instances with no shared state, so queuing a dose offline never refreshed the banner. Fixed with a small pub/sub event (`notifyMutationQueued`) that the sync engine listens for.

End-to-end verification: signed in, added a medicine, loaded the timeline online (caching it), went offline, reloaded the page (confirmed the offline banner and cache-served timeline — not a broken page), recorded a dose offline (confirmed the "saved on this device" indicator and the pending-changes banner), went back online (confirmed the banner cleared), and confirmed directly in Postgres that the dose event landed exactly once with the correct action.

Not built: a generic `/v1/sync` batch endpoint (only dose events are offline-capable — the highest-value single action; docs describe a fuller contract for future entities), offline medication add/edit, Background Sync API (retry-on-reopen is itself a documented fallback, not a shortcut), and storage-quota-based cache eviction.

**Stage 3 + 8, combined (this session):** `stored_objects`/`prescription_documents`/`prescription_extractions`/`extraction_candidates` tables + migration. `ObjectStorage` (Stage 1 interface) gains a second implementation, `LocalDiskObjectStorage`, alongside the existing R2 one — HMAC-signed tokens scoped to one object + one operation + a short expiry, mirroring real presigned S3/R2 URL semantics exactly, so production can swap in real R2 later with zero application-code changes outside the one factory function (ADR-12; no Docker available this session, so this stands in for MinIO). `DocumentsService`: authorize-upload → direct PUT → `complete` (never trusts the client's "done" claim — reads the bytes back, checks the real magic-byte signature against the declared content type, computes a sha256, quarantines on mismatch) → presigned download, all audited. `ExtractionService` runs real OCR (Tesseract.js, English only — no API key, no account, confirmed working before anything was built around it) synchronously in-request (a real deployment would push this to the worker queue; documented simplification), then applies deterministic, rule-based candidate detection — catalog brand/alias substring match, frequency pattern (`1-0-1`) or abbreviation (OD/BD/TDS/QID/SOS/HS) regex, food-instruction keyword match — never AI, never a guess presented as fact. Every candidate keeps the exact source line (`detectedText`) next to its proposal and requires an explicit per-field confirm/reject before it's used for anything (docs/09 §6); dose quantity/duration are deliberately never read from the photo (OCR digits are unreliable for a hazard-critical field) and stay a typed pick identical to manual entry. Creating a medication from an extraction requires the brand and frequency candidates specifically confirmed — an unrecognized medicine or an unconfirmed frequency falls back to the existing manual add flow rather than guessing. PWA: scan screen (kind picker, camera capture via `capture="environment"` or file/PDF choose, upload progress, processing status) and review screen (per-field detected-text quote + proposed value + Correct/Not this, dose picker, submit). Full audit trail per step (`document.upload_authorized/completed/downloaded`, `extraction.processed`, `extraction.field_confirmed/field_rejected`, `medication.created` with `source: "extraction"`) with no raw PHI in any context payload — verified directly against Postgres. 10 new e2e cases plus a real, non-mocked browser walkthrough (Playwright: sign in → photograph a synthetic prescription image → OCR → confirm all three fields → add the medicine → verify it and its correctly-derived dose schedule on `/medicines`).

Found and fixed a real correctness bug while testing the quarantine path: `completeUpload` threw the "invalid file" `ApiProblem` *inside* the `$transaction` callback that recorded the quarantine — Prisma rolls back the whole transaction when the callback throws, so the quarantine flag and its audit event were being silently discarded on every rejection, leaving the document stuck in `pending_upload` forever with no record of why. Fixed by committing the quarantine transaction first and throwing only after it succeeds; added a regression test asserting the quarantine status and audit row both persist across the failed request.

Not built: AI-based content simplification/translation and Indic-script/handwriting OCR (both **Blocked** on OD-11/OD-12 provider decisions). Async worker-queue OCR processing and PDF text extraction were synchronous-in-request/image-only limitations noted here originally — both are now built; see the async worker queue follow-up entry below.

**Stage 3 follow-up, this session — `cleanup-abandoned-uploads` cron:** reclaims storage from uploads that never finished — a presigned upload authorized but never completed/verified before its token expired, or a file quarantined for a bad signature and past a 7-day retention window. Deletes the physical object through the same `ObjectStorage.delete()` interface real R2 will use (no application logic to change when that swap happens), then marks both the `stored_object` and its `prescription_document` row `deleted` rather than hard-deleting, so the record stays for audit. Idempotent (only touches rows still `pending`/`quarantined`) and matches docs/25's pre-planned hourly schedule and job name exactly. Required widening `LocalDiskConfig.baseUrl` to optional (a delete-only consumer like this job never presigns a URL) and extending `cronEnvShape`/`JobContext` so job functions can read validated config, not just `prisma`/`log`. Verified live: authorized three real uploads (one never touched, one with real bytes written but never completed, one driven through the actual quarantine path), backdated their expiry/creation via Postgres, ran the compiled job directly, and confirmed both the physical files were removed and the DB rows updated correctly — then reran it to confirm a clean no-op the second time. Also fixed two stale entries in `infra/railway/README.md`'s cron table (`extend-scheduled-doses`, `reconcile-missed-doses` from Stage 4 were implemented but never added to that doc).

**Stage 4 follow-up, this session — web push reminders:** `notification_channels`/`notifications`/`notification_attempts`/`notification_preferences` tables + migration, modeled on docs/13's full notification schema (all documented channel/kind/status enum values kept, even the ones not implemented) so adding SMS/WhatsApp later is additive, not a redesign. Web push needs no external provider or account — a self-signed VAPID keypair (`web-push`, generated once and never regenerated) is enough, unlike SMS/WhatsApp which are genuinely blocked on OD-10. `VapidWebPushSender` (`@medpass/notifications`, alongside the existing `OtpSender`/`LogOtpSender`) wraps the `web-push` library and turns a 404/410 response into an explicit `gone` signal rather than a generic failure. API: `GET /push/vapid-public-key` (public — the key isn't sensitive), `POST /notification-channels/web-push` (+ `/unsubscribe`, upserted by a digest of the endpoint so re-subscribing never errors), `GET`/`POST /profiles/current/notification-preferences` (`manage_reminders` scope; push defaults **off** and wording defaults to the privacy-safe generic option — docs/16, never the medicine name unless the patient explicitly opts in). **Stage 11 follow-up, this session — application-level rate limiting:** docs/14, docs/18, and docs/26 are all explicit that rate limiting is layered — "Cloudflare rate limiting (per-IP budgets per flow) → application rate limiting (per-account, per-device)" — and that **the application layer must stand alone**: "Cloudflare is never the only protection against account takeover or OTP abuse." Cloudflare isn't provisioned in this sandbox (OD/platform-config, same as Railway/R2), which made the app-level gap real rather than theoretical: `ERROR_CODES.RATE_LIMITED` existed in `packages/domain` since early in the project but was never once thrown, and `CatalogController`'s own file header already claimed "rate-limit protected at the edge + app" — an intention that had never actually been built.

A new `RateLimitBucket` table (fixed-window counter, `key` + `windowStart` unique) backs `RateLimitService.checkAndIncrement()` — originally specced against Redis (`rate:` key namespace, docs/25) but there's no Redis in this sandbox, so Postgres is the counter store instead, the same documented substitution already used for the background-job queue. The `upsert`'s `ON CONFLICT DO UPDATE ... count = count + 1` increments atomically at the database level, so concurrent requests in the same window can never under-count each other. A new `RateLimitGuard`, registered globally alongside `AuthGuard` (and running first, so abusive traffic is rejected before any auth-related DB work), only acts on routes carrying a new `@RateLimit({ name, limit, windowSeconds })` decorator — everything else passes through unaffected. It runs regardless of authentication status, since the flows that most need it — OTP request/verify, public share access — are intentionally `@Public()` and have no session to gate them at all.

Applied to every "protected flow" from docs/26's list that actually exists in this codebase today: OTP request (10/hour/IP — a new layer on top of the existing 5/hour/phone limit `AuthService` already had, which this doesn't replace) and verify (20/hour/IP, on top of the existing 5-attempts-then-lockout per OTP record), public share access (30/minute/IP, shared across the JSON and PDF variants of the same token — they're the same abuse vector), catalog search (60/minute/IP), prescription-upload authorization (20/hour/IP), and the Telnyx delivery-status webhook (120/minute/IP — defense-in-depth on top of the Ed25519 signature check, which is the real protection there; a flood of even correctly-rejected signature attempts still costs real CPU). Account recovery, admin login, export generation, AI explanation/translation, and data deletion/export are all named in docs/26 too but don't exist as endpoints in this codebase yet — nothing to rate-limit there until they're built. A new `cleanup-rate-limit-buckets` cron (daily) deletes rows older than 24 hours — generous headroom given every window in use is an hour or less.

A real cross-test-suite correctness issue surfaced while wiring this in, not a production bug: the existing e2e suite makes 13 `/auth/otp/request` calls across 11 spec files, all using **different phone numbers** (each file's own test phone) but running from the **same test-client IP** — meaning a per-IP OTP-request budget would have started silently failing unrelated, previously-green tests the moment total cumulative calls crossed 10 in one `--runInBand` process, regardless of which file "owned" the failure. Fixed by adding `rate_limit_buckets` to every e2e spec file's existing per-file `TRUNCATE` statement (they already reset `otp_attempts`/`sessions`/`users` etc. per file for exactly this isolation reason — this is the same pattern, not a new one).

Verified live against the real running API, not just the test suite: 62 real requests to the real catalog-search endpoint returned a real `429` with `retry-after: 49` on request 61 (limit 60/min); the resulting `rate_limit_buckets` row's `count` matched the real request count exactly; backdating that row's `window_start` 25 hours and running the real compiled `cleanup-rate-limit-buckets` binary deleted exactly that one row and left the others (still within the 24h retention) untouched. 6 new e2e cases (`rate-limit.e2e-spec.ts` — window enforcement, independent keys, window reset, atomic concurrent increments, a real `@Public()` route hitting its real limit end-to-end with the header present, and one budget's exhaustion not affecting another's) — full suite re-verified green (131 tests, 15 suites).

Not built: WAF, Turnstile, and Cloudflare's own rate limiting (all **Requires platform configuration** — Cloudflare isn't provisioned), rate limits on account recovery/admin login/export/AI explanation/translation (don't exist as endpoints yet), and a behavioral-detection layer beyond fixed budgets (docs/26 mentions this as the last layer; a fixed-window counter is the budget enforcement, not anomaly detection).

**Stage 5 follow-up, this session — service-worker update-notification banner:** the one remaining item from Stage 5's original scope that wasn't Background Sync API (which has no real fallback-free value here — retry-on-reopen, already built, is itself one of docs/32's mandated fallbacks, not a shortcut standing in for it). **Stage 11 follow-up, this session — cost controls:** docs/31's "Enforced limits" table names several concrete, unbuilt guardrails whose explicit purpose is throttling abuse/waste, never patient-critical behavior ("do not weaken clinical safety to reduce cost — cost controls throttle abuse and waste, never patient-critical reminders or safety evaluations"). The storage quota (200MB/profile, soft warn at 80%) and upload quota (20/user/day) both live in `DocumentsService.authorizeUpload` (`apps/api`). **Stage 4 follow-up, this session — auto-revoke an SMS channel on a confirmed permanent delivery failure:** the last named "not done" item from the earlier Telnyx delivery-status webhook follow-up. Web push already revokes a subscription on a 404/410; SMS had the webhook recording `delivered`/`failed` outcomes but never acting on `failed`, deliberately deferred because Telnyx's failure-code taxonomy wasn't understood well enough to safely tell "this destination number is dead" apart from "temporary account-level block" — the one real code seen in this account, 40329 (toll-free not verified), is itself an account-level block, not evidence of anything about the destination.

Rather than guess, fetched Telnyx's own published messaging error-code reference directly (support.telnyx.com/en/articles/6505121) before writing any classification logic. Built a deliberately narrow **allowlist** (`PERMANENT_DESTINATION_FAILURE_CODES` in `@medpass/notifications`) of only the codes confirmed destination-specific and permanent: `40001` (landline/non-routable), `40012` (destination number unowned/deactivated), `40300` (recipient sent STOP — also a consent/compliance requirement to honor), `40310` (malformed 'to' address) — an allowlist rather than "everything except a known-safe list" because a false positive here silently stops reminding someone still reachable, a worse failure mode than reacting slowly to a genuinely dead number. `40329` stays excluded, as does `40003` ("blocked as spam — permanent") despite the name — Telnyx's own text says that one permanently blocks the *sending* number, not the destination, so treating it as a per-recipient signal would have been exactly the kind of mistake this deferral was guarding against.

`recordTelnyxDeliveryOutcome` (`apps/api/src/modules/notifications/notifications.service.ts`) now runs inside a transaction: updates the `NotificationAttempt` as before, and — only for a `channel: "sms"` attempt with a confirmed permanent-destination failure — guarded-updates the linked `NotificationChannel` to `status: "revoked"` (`updateMany` with `status: { not: "revoked" }` in the `where`, so a retried/duplicate webhook delivery can't write a second audit event) and writes a new `notification.channel_revoked` audit event (`actorType: "system"`, since this is an automatic consequence of a delivery outcome, not a user action) — closing a real gap the web-push revoke path already had (it writes no audit event at all; this one does). No new "is this channel revoked" check needed anywhere else: `resolveRecipients`/`resolveEscalationRecipients` in `apps/cron`'s `detect-due-reminders.ts` already only ever select `status: "active"` channels, so a revoked SMS channel is automatically excluded from every future send.

Tested: 4 new unit tests in `packages/notifications` (40329 explicitly asserted `permanentDestinationFailure: false`, a STOP code asserted `true`, the sending-number-blocked 40003 asserted `false`) plus 3 new e2e cases in `telnyx-webhook.e2e-spec.ts` (a STOP-code webhook revokes the channel and writes exactly the expected audit event; a 40329 webhook leaves the channel `active`; the same STOP webhook delivered twice writes only one audit event, not two) — full suite green throughout (170 api tests, 19 notifications unit tests). Deployed to both `medpass-dev` and `medpass-prod` and confirmed live.
