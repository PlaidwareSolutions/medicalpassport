**Stage 5 (partial, this session):** `packages/offline-sync` — an IndexedDB wrapper (via `idb`) with four object stores: `medications` and `timeline` caches (both keyed by profile + a variant/date so "current" vs "all" medications and different days' timelines don't collide), a `mutations` outbound queue keyed by `clientMutationId`, and `meta` for last-synced timestamps. 11 unit tests against `fake-indexeddb`, run in a real (simulated) IndexedDB, not mocked-out function calls. `lib/timeline.ts` and `lib/medications.ts` now cache every successful fetch and fall back to the cache on a genuine network failure (distinguished from a server-side rejection: an `ApiError` means the server responded and is shown as a real error; anything else means `fetch()` itself failed, which is the offline signal). Recording a dose while offline queues the mutation instead of losing it — the same `clientMutationId` the API already required for idempotency (built in Stage 4) makes replay exactly-once safe even after the app is closed and reopened. `useSyncEngine` flushes the queue on app open, on the browser's `online` event, and on tab visibility change (docs/32's mandated fallback for browsers without Background Sync) and drives a genuinely honest status banner — online/offline/syncing/failed/pending-count/last-synced are real, distinct states, not a collapsed boolean.

Verified with an actual Chromium browser via Playwright (`context.setOffline(true)`), not just unit tests — offline behavior is fundamentally about browser network events and IndexedDB, which unit tests can't exercise end-to-end. This caught two real bugs before they shipped:
1. `SessionProvider` treated a network failure on a fresh page mount as "signed out" and redirected to `/welcome` — meaning reopening the app while offline looked exactly like being logged out, defeating the entire feature. Fixed: a network failure (not a 401) with a locally-stored profile id now stays "ready" and lets each screen serve its own cached data, since a stored profile id is evidence of a real prior session.
2. The pending-mutation count had no way to update when a new mutation was queued — `recordDoseEvent` and `useSyncEngine` are two independent hook instances with no shared state, so queuing a dose offline never refreshed the banner. Fixed with a small pub/sub event (`notifyMutationQueued`) that the sync engine listens for.

PWA: scan screen (kind picker, camera capture via `capture="environment"` or file/PDF choose, upload progress, processing status) and review screen (per-field detected-text quote + proposed value + Correct/Not this, dose picker, submit). Found and fixed a real correctness bug while testing the quarantine path: `completeUpload` threw the "invalid file" `ApiProblem` *inside* the `$transaction` callback that recorded the quarantine — Prisma rolls back the whole transaction when the callback throws, so the quarantine flag and its audit event were being silently discarded on every rejection, leaving the document stuck in `pending_upload` forever with no record of why. **Stage 6 follow-up, this session — schedule-conflict and dose-differs-from-prescription checks:** docs/09 names these as finding categories 9–10 but, unlike the interaction/allergy checks, never pins down their mechanics anywhere in the planning docs — so both are defined here purely from data the app already has, never fabricated, and documented as an explicit engineering judgment call alongside the rest of Stage 6's "requires clinical validation" caveat. **Schedule conflict**: fires when a fixed-frequency medicine (OD/BD/TDS/HS/PATTERN) has no active `MedicationSchedule` — the reminder infrastructure silently not matching what the confirmed instruction implies it should (`moderate`) — or when a PRN medicine has one anyway, contradicting "as needed" (`low`). **Dose differs from confirmed prescription**: compares a medicine's very first confirmed instruction against the one in force now (instructions are copy-on-write per docs/13, so this is a plain diff over the patient's own history) and flags if the dose or frequency changed, `moderate` severity — never a judgment about whether a doctor authorized the change, just that a change happened.

Found and fixed a real, pre-existing bug while wiring the finding titles for these two new categories: `FindingCard`'s title lookup is `t(\`safety.finding.${finding.category}\`)`, but the dictionary keys for the four original categories used shortened names (e.g. `safety.finding.exact_duplicate`) that never matched the real stored category strings (`exact_ingredient_duplication`) — so those titles have silently rendered as the raw, untranslated key string since Stage 6 shipped, for every category except `uncertain_normalization` (whose short name happened to already match). Never caught because this dev database had only ever produced `uncertain_normalization` findings until this session's live testing generated the others for real. Fixed by renaming the four dictionary keys to the real category strings, in all four locales, rather than perpetuating the mismatch for the two new categories too.

Also found and fixed a second real gap surfaced by testing dose-differs-from-prescription honestly: docs/09 lists "medication changes" as a safety re-evaluation trigger, but `MedicationsService.update()` never actually called `SafetyEvaluationService.evaluate()` — only `create()` and the status-change endpoint did. Editing a medicine's dose or frequency silently skipped re-evaluation entirely, so this check (and any future one keyed off instruction edits) would never have fired without a manual re-check. Fixed by calling `evaluate(profileId, "medication_updated")` whenever an instruction changes.

Verified live end-to-end against real data, not just unit tests: created a fixed-frequency medicine (confirmed it initially passes clean), ended its schedule via Postgres, and confirmed the missing-schedule finding appeared with the right severity and wording; created a PRN medicine (confirmed no schedule exists by default), inserted a stray active schedule row, and confirmed the PRN-conflict finding appeared; edited a medicine's dose via the real API with no manual evaluate call and confirmed dose-differs appeared automatically; screenshotted the rendered Safety screen in a real production-mode browser before and after the title-key fix to see the raw-key bug directly, then confirm it was actually fixed. 9 new e2e cases plus 9 new unit tests.

**Stage 7 follow-up, this session — PDF export:** doctor-visit summaries and public share links can now be downloaded as a real, printable PDF (`GET /profiles/current/visit-summary/pdf`, `GET /public/shares/:token/pdf`), matching OD-14's assumption of server-side headless Chromium rather than a client-side PDF library, which can't reliably paginate/print arbitrary HTML+CSS. OD-14 also assumed this would run behind a BullMQ worker queue, but there's no Redis in this sandbox (the same constraint Stage 3/8's OCR hit) — rendering happens synchronously in the API request instead, a documented simplification that needs no code change here to move behind a queue later, just a different caller. The PDF is never stored: it's regenerated fresh on every request, same as the live JSON summary, for the same reason (docs/12 H-12 — a stale medication list handed to a doctor is a safety risk, so there's nothing to go stale and nothing to clean up). Reuses the exact same aggregation and section-filtering as the JSON endpoints, so a share's PDF respects whatever sections the patient chose to include, and the public path is audited through the same `share.accessed` event as the JSON path — no new audit action needed. PWA: a "Download as PDF" button on doctor-visit mode (authenticated, blob-fetched with the browser's Download API) and a plain download link on the public share page (no auth needed, so no blob indirection required).

Puppeteer is ESM-only, which broke in two different ways before landing: a static `import` fails ts-jest's CommonJS transform outright, and even TypeScript's own *dynamic* `import()` gets silently downleveled to a `require()` call under a CommonJS module target — both hit the same "can't require() an ESM package" wall. Found and fixed a real bug during live verification, not caught by curl-testing alone: the lazy-singleton browser instance used `??=`, which permanently caches whatever it's assigned — including a *rejected* promise. **Stage 4 follow-up, this session — quiet hours + caregiver reminder fan-out:** `NotificationPreference` gains a patient-configurable quiet-hours window (`quietHoursEnabled`/`quietHoursStart`/`quietHoursEnd`, default on, 22:00–07:00, same fixed-IST-offset simplification the scheduling engine already uses). `detect-due-reminders` is now two passes instead of one: detection creates a `pending` Notification the moment a dose becomes due, and a separate dispatch pass attempts every still-`pending` notification on every tick — so a reminder that lands inside quiet hours is deferred, not dropped, and is retried automatically as soon as quiet hours end, however many ticks later that is. Recipients are resolved fresh on every dispatch attempt: the profile owner plus any caregiver holding an active `manage_reminders` or `full_management` permission on that profile, provided they have their own registered push device — consented reminder fan-out, not the separate (unbuilt) missed-dose escalation flow. `ReminderSettings` (PWA) gained the quiet-hours toggle and start/end time pickers, saved immediately like the existing privacy-wording control, plus a one-line note that caregivers with reminder access get these too.
