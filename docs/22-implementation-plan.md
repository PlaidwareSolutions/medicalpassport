## This session's deliverable detail

**Stage 1:** Turborepo + pnpm; `apps/{patient-web,admin-web,api,worker,cron,mobile-native*}`; all 17 packages scaffolded; Dockerfiles; docker-compose (PG+Redis dev); API health/logging/correlation/`/v1`; PWA manifest + Serwist SW + offline fallback + bottom-nav shell; admin shell; CI (lint/typecheck/test/build/migration-check/gitleaks); `infra/railway` + `infra/cloudflare` configs as code/docs; `.env.example` per app.

**Stage 2:** Prisma schema (★ subset of [13](13-data-model.md)) + migrations + seed; API modules: auth (OTP/sessions/devices), profiles, caregivers, consents, catalog search, patient medications (idempotent writes, rowVersion, audit); PWA screens: welcome/language/OTP/create-profile/home/medicines list/add (search+manual)/detail/profile area basics.

**Stage 4 (partial, this session):** `medication_schedules`/`scheduled_doses`/`dose_events` tables + migration; `SchedulingService` derives a schedule from the confirmed instruction on medication create/update, regenerates on pause→current, and clears future undone doses on pause/stop/delete (deletes rather than soft-cancels — an "upcoming" row is guaranteed eventless, so this lets resume cleanly regenerate the same slots); `TimelineService` + `GET /profiles/current/timeline` + `POST /doses/:id/events` (idempotent) + `POST /profiles/current/doses/prn-events`; `extend-scheduled-doses` and `reconcile-missed-doses` cron jobs (Asia/Kolkata fixed-offset simplification, documented); PWA: screen 8 (Today's timeline, grouped by slot) + `DoseCard` component (one-tap Taken/Skip/Snooze + "more options" for the remaining four dose states) + Home now shows real due-now/due-next/missed sections instead of a static banner. Fixed a timezone bug during review where calendar-day derivation used the raw UTC date instead of the IST-shifted date (would have materialized the wrong day for ~5.5h daily). 6 new e2e tests. Not built: reminder dispatch (push/SMS/WhatsApp), refill/completion reminders, reminder privacy wording UI.

**Stage 6 (partial, this session):** `safety_evaluations`/`safety_findings`/`safety_finding_actions` tables + migration. Pure, directly-unit-tested rule functions (`safety-rules.ts`, 9 unit tests) for exact/partial ingredient duplication (by shared ingredient across normalized products), therapeutic-class duplication (skipping pairs already caught at the ingredient level), drug-allergy matching, and uncertain-normalization (any unmatched/free-text medicine gets its own finding rather than being silently excluded from checks — docs/09 hazard H-23). Rule keys/versions are code constants rather than a maker-checker-approved table, since that governance workflow needs an appointed clinical lead (OD-6) this pass doesn't have; traceability (source/rule version/app version/evaluation time/input snapshot) is still fully recorded per finding. `SafetyEvaluationService.evaluate()` re-runs on medication add, medication restart, and allergy add, and is immutable per run — "current findings" means the latest evaluation's findings only. `GET /profiles/current/safety/findings` + `POST /findings/:id/actions` (acknowledge/note/reviewed-with-professional/resolved — a finding is never deleted, only actioned). Filled a real Stage 2 gap: there was no allergy-entry screen at all, so the drug-allergy rule had nothing to match against — added `POST /profiles/current/allergies` exact/synonym-name auto-linking against the ingredient catalog (never fuzzy-matched) and a full Allergies screen (list + add form). Seeded one more product (Novamox/Amoxicillin, with "Penicillin" as a synonym) so the allergy check has something real to demo. PWA: `FindingCard` component carrying the four mandatory statements (docs/02) on every finding, Safety screen (open + resolved sections), and Home's "Needs review" section is now real instead of absent. 6 new e2e tests covering all four rule categories plus the acknowledge lifecycle and the "no fuzzy guess" allergy case. Not built: drug-drug interaction, drug-condition, food, and alcohol checks (blocked on OD-4 licensed data or clinically-reviewed content — never fabricated), schedule-conflict and dose-differs-from-prescription categories, clinical-lead sign-off (Gates 1–3 of [34](34-clinical-validation-plan.md)).

Two turbo.json config gaps found and fixed during this session (both would silently affect CI too): the `test` task's env allowlist was missing several secrets the API needs to boot, and `typecheck` depended only on upstream packages' builds (`^build`), not the package's own build — so a Next.js app's typecheck could run before `next build` generated the `.next/types` it needs, and did.

**Stage 7 (partial, this session):** `share_packages`/`share_links`/`share_access_events` tables + migration. `VisitSummaryService` aggregates identity/allergies/conditions/current-medications/recent-changes/open-concerns live from current data — the same aggregation backs both the patient's own doctor-visit mode (screen 28, always full detail) and the public share payload (filtered to whichever sections the patient opted into). `SharingService`: opaque tokens hashed at rest (never stored raw, same pattern as session tokens), ≤30-day expiry, revocation, and an append-only access log that records every attempt — not just successes — so expired/revoked/invalid probing is visible to the patient too. `GET /public/shares/:token` is unauthenticated by design and always returns the same generic "no longer available" message regardless of whether the token was never valid, expired, or revoked, so a probing attempt learns nothing. PWA: doctor-visit mode screen, share-creation screen (selective sections, expiry picker, client-side QR code rendering via `qrcode` — no external service call), active-shares list with per-share access history and revoke, and a fully standalone public share page with no auth and no app-shell chrome. 8 new e2e tests.

Found and fixed a real observability bug while verifying this stage's error-path tests: `LoggingInterceptor` read `res.statusCode` inside RxJS `finalize()`, which fires *before* `ProblemDetailsFilter` actually sets the status on a thrown-exception path — so every 4xx/5xx response has been logged as whatever Express's default (200) was since Stage 1, silently undermining every error-rate dashboard and alert this system would ever have. Fixed by moving the log line to the response's `finish` event, which only fires once the status is truly final regardless of the success/error path's internal timing; added 3 regression tests pinning this down directly (success path, thrown-exception path, and a synthetic "status changes between handler and finish" case matching exactly what was silently wrong before).

Not built in Stage 7: PDF export, WhatsApp-text export, security review (required before any of this is exposed to real doctors/pharmacists).

**Stage 5 (partial, this session):** `packages/offline-sync` — an IndexedDB wrapper (via `idb`) with four object stores: `medications` and `timeline` caches (both keyed by profile + a variant/date so "current" vs "all" medications and different days' timelines don't collide), a `mutations` outbound queue keyed by `clientMutationId`, and `meta` for last-synced timestamps. 11 unit tests against `fake-indexeddb`, run in a real (simulated) IndexedDB, not mocked-out function calls. `lib/timeline.ts` and `lib/medications.ts` now cache every successful fetch and fall back to the cache on a genuine network failure (distinguished from a server-side rejection: an `ApiError` means the server responded and is shown as a real error; anything else means `fetch()` itself failed, which is the offline signal). Recording a dose while offline queues the mutation instead of losing it — the same `clientMutationId` the API already required for idempotency (built in Stage 4) makes replay exactly-once safe even after the app is closed and reopened. `useSyncEngine` flushes the queue on app open, on the browser's `online` event, and on tab visibility change (docs/32's mandated fallback for browsers without Background Sync) and drives a genuinely honest status banner — online/offline/syncing/failed/pending-count/last-synced are real, distinct states, not a collapsed boolean.

Verified with an actual Chromium browser via Playwright (`context.setOffline(true)`), not just unit tests — offline behavior is fundamentally about browser network events and IndexedDB, which unit tests can't exercise end-to-end. This caught two real bugs before they shipped:
1. `SessionProvider` treated a network failure on a fresh page mount as "signed out" and redirected to `/welcome` — meaning reopening the app while offline looked exactly like being logged out, defeating the entire feature. Fixed: a network failure (not a 401) with a locally-stored profile id now stays "ready" and lets each screen serve its own cached data, since a stored profile id is evidence of a real prior session.
2. The pending-mutation count had no way to update when a new mutation was queued — `recordDoseEvent` and `useSyncEngine` are two independent hook instances with no shared state, so queuing a dose offline never refreshed the banner. Fixed with a small pub/sub event (`notifyMutationQueued`) that the sync engine listens for.

End-to-end verification: signed in, added a medicine, loaded the timeline online (caching it), went offline, reloaded the page (confirmed the offline banner and cache-served timeline — not a broken page), recorded a dose offline (confirmed the "saved on this device" indicator and the pending-changes banner), went back online (confirmed the banner cleared), and confirmed directly in Postgres that the dose event landed exactly once with the correct action.

Not built: a generic `/v1/sync` batch endpoint (only dose events are offline-capable — the highest-value single action; docs describe a fuller contract for future entities), offline medication add/edit, Background Sync API (retry-on-reopen is itself a documented fallback, not a shortcut), and storage-quota-based cache eviction.

**Stage 3 + 8, combined (this session):** `stored_objects`/`prescription_documents`/`prescription_extractions`/`extraction_candidates` tables + migration. `ObjectStorage` (Stage 1 interface) gains a second implementation, `LocalDiskObjectStorage`, alongside the existing R2 one — HMAC-signed tokens scoped to one object + one operation + a short expiry, mirroring real presigned S3/R2 URL semantics exactly, so production can swap in real R2 later with zero application-code changes outside the one factory function (ADR-12; no Docker available this session, so this stands in for MinIO). `DocumentsService`: authorize-upload → direct PUT → `complete` (never trusts the client's "done" claim — reads the bytes back, checks the real magic-byte signature against the declared content type, computes a sha256, quarantines on mismatch) → presigned download, all audited. `ExtractionService` runs real OCR (Tesseract.js, English only — no API key, no account, confirmed working before anything was built around it) synchronously in-request (a real deployment would push this to the worker queue; documented simplification), then applies deterministic, rule-based candidate detection — catalog brand/alias substring match, frequency pattern (`1-0-1`) or abbreviation (OD/BD/TDS/QID/SOS/HS) regex, food-instruction keyword match — never AI, never a guess presented as fact. Every candidate keeps the exact source line (`detectedText`) next to its proposal and requires an explicit per-field confirm/reject before it's used for anything (docs/09 §6); dose quantity/duration are deliberately never read from the photo (OCR digits are unreliable for a hazard-critical field) and stay a typed pick identical to manual entry. Creating a medication from an extraction requires the brand and frequency candidates specifically confirmed — an unrecognized medicine or an unconfirmed frequency falls back to the existing manual add flow rather than guessing. PWA: scan screen (kind picker, camera capture via `capture="environment"` or file/PDF choose, upload progress, processing status) and review screen (per-field detected-text quote + proposed value + Correct/Not this, dose picker, submit). Full audit trail per step (`document.upload_authorized/completed/downloaded`, `extraction.processed`, `extraction.field_confirmed/field_rejected`, `medication.created` with `source: "extraction"`) with no raw PHI in any context payload — verified directly against Postgres. 9 new e2e cases plus a real, non-mocked browser walkthrough (Playwright: sign in → photograph a synthetic prescription image → OCR → confirm all three fields → add the medicine → verify it and its correctly-derived dose schedule on `/medicines`).

Found and fixed a real correctness bug while testing the quarantine path: `completeUpload` threw the "invalid file" `ApiProblem` *inside* the `$transaction` callback that recorded the quarantine — Prisma rolls back the whole transaction when the callback throws, so the quarantine flag and its audit event were being silently discarded on every rejection, leaving the document stuck in `pending_upload` forever with no record of why. Fixed by committing the quarantine transaction first and throwing only after it succeeds; added a regression test asserting the quarantine status and audit row both persist across the failed request.

Not built: AI-based content simplification/translation and Indic-script/handwriting OCR (both **Blocked** on OD-11/OD-12 provider decisions), async worker-queue OCR processing (synchronous in-request this pass), PDF text extraction (image formats only).
